# 开发流程定义规则

## 目的

本规则用于约束 AI 在需求达到可开发状态后的开发过程。

开发流程负责决定：

```text
写代码前还需要明确什么
→ 需要产生哪些实际产物
→ 什么时候允许编码
→ 如何拆成可独立完成的小流程
→ 写完后如何完成开发自检并交给测试验证
```

## 开发单元

开发以一个有业务意义、能够独立完成并验证的小流程为基本单元。

```text
简单需求
→ 一个开发流程

复杂需求
→ 拆成多个小流程
→ 记录依赖关系
→ 每个小流程重复执行同一个开发闭环
```

不按单个函数机械拆分，也不把整个大型需求一次性交给 AI 编码。

同一需求内的小流程记录在 `loop.yaml.subflows`；可独立确认、交付、回滚、并行或超过单次上下文时，升级为父子 Loop。状态、依赖、范围和聚合规则遵守[AgentLoop 状态机](../agentloop/AgentLoop状态机.md)与[产物与目录协议](../agentloop/产物与目录协议.md)。

## 唯一核心闭环

```text
读取已确认需求和现有上下文
→ 选择主开发流程
→ 拆出一个可独立完成的小流程
→ 补齐真正需要的编码前设计
→ 编码前确认
→ 编写代码
→ 执行编译、静态检查和必要单元测试
→ 修正开发自检发现的问题
→ 形成测试交接信息
→ ready_for_verification
```

开发流程分类只用于选择编码前需要补什么，不为分类本身制造额外文档或固定仪式。

## 阶段产物规则

开发流程中的正式阶段必须产生明确产物或可验证的状态变化。

产物可以是：

- 原型、流程图或模型
- 接口契约或数据库脚本
- 代码、配置或迁移脚本
- 测试代码和运行结果
- `development.md` 或 trivial `work.md` 中的确认记录或状态

每个阶段只需明确：

```text
输入
→ 要完成的操作
→ 产物或状态变化
→ 检查方式
→ 进入下一步的条件
```

不要求每个阶段单独创建文档。“分析完成”“已经考虑”不能作为产物。

## 最小文件规则

`standard/composite` 默认只维护一个 `development.md`；`trivial` 与需求记录合并为 `work.md`。用于记录：

- 目标和范围
- 当前系统关键事实
- 选用的主流程和触发的条件设计
- 编码前产物或其文件引用
- 小流程及依赖
- 编码状态
- 开发自检结果和测试交接信息

其他文件仅在本身就是有效产物时创建，例如原型、接口契约、数据库脚本、代码和测试。

成功时不再重复生成分析报告、设计总结、执行记录和完成报告。开发阶段的完成证据是实际代码、必要单元测试和开发自检结果。

## 编码前产物选择

只产生当前需求真正需要的产物：

```text
修改现有系统
→ 相关入口、调用关系、可复用能力、影响范围和不变行为

涉及 UI 或交互
→ 开发设计原型或可执行的交互步骤

涉及角色、流程或状态变化
→ 业务流程和状态转换规则

涉及数据结构
→ 数据模型、约束和数据库变更脚本

涉及新增或修改接口、消息或系统调用
→ 必须产生接口或消息契约及关键样例

复用现有接口
→ 必须记录接口引用并核对其满足当前需求

涉及复杂领域规则
→ 领域概念、业务规则和代表性样例

涉及架构取舍或非功能要求
→ 关键架构决策、边界和可验证指标

涉及迁移或兼容
→ 映射、迁移、核对、停止和回滚方式

涉及缺陷修复
→ 可复现问题、完整调用链、根因证据和最小修复位置

涉及技术可行性不确定
→ 最小实验、判定指标和真实实验结果
```

未触发的产物不得为了流程完整而生成。已有产物满足需要时直接复用或补充。

## 现有系统调查规则

对现有系统进行新增、修改、修复、重构、迁移或删除时，编码前必须调查实际实现。

调查范围按需求裁剪，至少能够回答：

- 修改从哪里进入
- 主要调用方和数据流是什么
- 哪些已有能力可以复用
- 哪些模块和行为会受影响
- 哪些行为必须保持不变
- 现有测试如何运行

不允许只根据需求重新设计一套与当前代码脱节的实现。

## 原型归属与退回规则

```text
需求原型
→ 在需求核对阶段确认产品范围、用户路径和主要业务流程

开发设计原型
→ 在开发阶段、编码前补齐页面状态、交互细节、组件行为和数据需求
```

已有需求原型时应在其基础上细化。需求阶段没有原型时，开发阶段仍可按需制作开发设计原型。

如果开发设计原型改变业务范围、核心流程或验收标准，必须退回需求核对阶段重新确认。

## 编码前确认

只有同时满足以下条件，流程状态才能变为“允许编码”：

```text
需求和验收标准已经确认
→ 当前小流程的范围明确
→ 必需的编码前产物已经完成
→ 已触发的条件产物已经完成
→ 关键冲突和待确认问题已经关闭
→ 实现任务能够追溯到需求和设计
→ 已明确需要交给测试阶段验证的业务流程和风险
```

“已经生成计划”不等于“允许编码”。

## 编码自检与测试交接

开发阶段只负责低成本开发自检：

- 编译或构建
- 类型检查和静态检查
- 对新增或修改的非简单逻辑编写单元测试
- 运行与当前修改直接相关的已有单元测试
- 接口契约、Schema 和数据库脚本的语法或结构检查

开发自检用于尽早发现代码错误，不代替需求验收和流程级测试。

开发完成后，向测试阶段交付：

- 已实现的小流程和影响范围
- 对应需求及验收标准
- 新增或修改的接口、数据和状态
- 开发阶段新增的单元测试
- 建议重点验证的正常、分支和失败场景
- 所需测试账号、数据、环境或开关
- 已知限制和未解决问题

测试 Agent 再按照[测试验证流程体系总览](../verification/测试验证流程体系总览.md)选择执行器并完成流程级验证。

## 流程组合规则

一个需求原则上选择一个主开发流程，其他流程只在出现对应问题时作为子流程组合。

组合时只记录：

- 主流程
- 触发的子流程
- 子流程交付的产物
- 小流程之间的依赖

组合流程不得重复生成相同产物。能够补充现有产物时，不新建另一份。

每个复合子流程必须有独立状态、范围、Git 检查点和测试交接；不同子流程可以交错开发和验证，父状态按状态机聚合。

## 完成条件

```text
当前小流程代码已经完成
+ 必要的编码前产物已经落地
+ 编译、静态检查和相关单元测试已经通过
+ 非简单新增或修改逻辑有对应单元测试
+ 测试交接信息已经形成
+ 状态明确为 ready_for_verification 或 blocked
```

`ready_for_verification` 表示开发阶段完成，不表示需求已经通过测试验收。文档数量不作为完成条件。

## 最小流程模板

```text
# 开发流程名称

## 目标与范围

## 当前系统关键事实

## 选择的主流程

## 触发的条件设计及产物

## 小流程与依赖

## 编码前确认

## 实现状态

## 开发自检与测试交接
```

简单流程可以删除未触发的空章节。

## 新增或修改开发流程

新增流程前依次检查：

```text
已有流程能否覆盖
→ 是否只需增加一个条件产物
→ 是否只需组合一个已有子流程
→ 确实存在新的编码前决策路径时，才新增流程
```

新增流程仍必须复用本规则中的核心闭环、最小文件规则和完成条件。
