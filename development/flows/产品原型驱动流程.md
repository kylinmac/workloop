# 产品原型驱动流程

## 何时选择

页面状态、交互方式、用户路径或用户可见结果是当前最大的开发不确定性。

本流程交付生产可用系统，不交付 Demo、纯前端复刻或以高保真原型冒充的业务实现。高保真原型只决定 UI 实现依据，视觉通过不代表业务功能通过。

## 进入输入

- 已确认需求、范围和验收标准
- 需求原型；需求阶段已经产生时
- 现有页面、组件和设计规范；修改现有系统时

## 编码前阶段与产出

| 阶段 | 操作 | 明确产出 | 检查与出口 |
|---|---|---|---|
| 1. 建立基线 | 核对需求原型、现有界面和验收标准 | `development.md` 中的原型来源、现有页面入口、不可改变行为 | 原型内容能追溯到需求 |
| 2. 固化行为清单 | 由控制程序扫描已确认原型源文件，记录源摘要、事件入口和导航分支 | `prototype-behavior-inventory.yaml` | 清单由 `prototype-scan` 生成且源摘要未过期，禁止手写替代 |
| 3. 建立实现矩阵 | 逐页提取路由、区域布局、控件、交互、状态、数据、权限、响应式和允许偏差 | `prototype-implementation-matrix.yaml` | 需求声明的每个原型页面恰好有一条完整页面记录；每个行为清单项恰好映射一次；复合 Loop 还明确 `subflow_id` |
| 3. 形成设计原型 | 制作或细化页面、弹窗、导航和响应式行为 | 可操作的开发设计原型 | 核心用户路径可以从头操作到尾 |
| 4. 补齐交互状态 | 补充正常、加载、空、错误、无权限等状态 | 原型中的页面状态；`development.md` 中的触发条件和结果 | 每个关键操作都有可见结果，异常状态无断点 |
| 5. 拆用户流程 | 写出前置条件、连续点击步骤、每步预期和最终结果 | 可独立实现的用户流程清单 | 每个流程能够独立操作并判断结果 |
| 6. 提取开发依赖 | 从原型提取组件、数据、权限和状态需求 | `development.md` 中的开发依赖；按需生成状态规则和数据库脚本 | 每个界面数据和操作都有明确来源及处理方 |
| 7. 确认接口契约 | 逐个检查用户操作、页面数据和状态变化所需的前后端调用 | 新增或修改接口的 OpenAPI/API 文档；复用接口的明确引用 | 原型中的服务端操作均有接口承载，契约可解析，字段和页面状态一致 |
| 8. 切分实现 | 按用户流程切分前端、后端及联调顺序 | 功能切片和依赖关系 | 每个切片都能产生可运行结果，前后端可以依据同一契约开发 |

除开发设计原型、契约或数据库脚本外，其余内容默认合并在 `development.md` 中。

`prototype-implementation-matrix.yaml` 使用 `prototype-matrix.schema.json`。每页必须记录：

- 原型文件、产品路由和所属子流程
- 页面区域、布局及必须存在的控件
- 控件交互、状态变化及对应验收 ID
- 加载、空、错误、无权限状态
- 数据/API 来源和权限行为
- 响应式要求
- 允许偏差及理由
- 每项可见业务记录/指标的 seed、数据库、正式 API 字段或服务端计算口径，以及无数据空态
- 每个 interaction 的数据库前置状态、用户操作、`effect`、OpenAPI `operation_id`、预期响应、持久化断言、readback operation、刷新/重登、失败、权限、下游消费和审计断言
- 每个 interaction 对应的 `source_behavior_ids` 和是否必须进入旅程的 `journey_required`
- 导航交互的起始路由、真实点击/提交触发方式、全部条件分支及目标路由；目标 URL 直达不得作为交互实现或验证依据

Schema 通过后，控制程序还会检查原型页集合完全一致、原型摘要有效、扫描行为与矩阵一一对应、导航分支与用户旅程完整、区域/控件引用有效，以及复合切片页面归属。矩阵漏掉一个源交互或状态跳转时，`development_preparing → developing` 和子流程进入 `developing` 均失败。

选择 `product-prototype` 时控制程序自动要求 `prototype-behavior-inventory`、`prototype-implementation-matrix`、`user-flow-slices` 和 `api-contract`。先在 `development_preparing` 执行 `prototype-scan`；原型改动后摘要失效，必须重扫并重新映射。服务端 interaction 的 operation 必须真实存在于 `files.api_contract` 指向的 OpenAPI；纯客户端交互必须使用 `client_only_exempt` 并给出理由。接口缺失时应补充 `data-contract` 或 `business-process`，不得降级为 Toast、跳转或本地状态变化。

## 条件分支

```text
发现复杂角色、状态或异常
→ 补充业务流程驱动阶段产物

发现新数据结构或系统调用
→ 补充数据与契约驱动阶段产物

开发设计原型改变范围、核心流程或验收标准
→ 退回需求核对阶段重新确认
```

接口契约至少包含：

- 接口用途、方法和路径
- 认证与权限要求
- 请求字段、类型和约束
- 响应字段及成功样例
- 失败结果和错误码
- 幂等要求；存在重复提交风险时

只有纯静态页面或所有调用均复用已确认且满足需求的现有接口时，才不新增接口文档；此时仍需记录复用接口引用。

## 编码前确认

```text
原型可以实际操作
+ prototype-behavior-inventory 与当前原型摘要一致且全部行为已映射
+ prototype-implementation-matrix 完整且与需求原型逐页一致
+ 关键操作、页面状态和结果完整
+ 新增或修改的接口契约已经确认
+ 复用接口已经核对能够满足原型
+ 用户流程已经切片
+ 每个用户流程有验证方式
→ 允许编码
```

用户流程切片必须至少包含一条完整生产旅程：创建 → 编辑 → 保存 → 刷新 → 重新登录 → 查询 → 后续流程消费 → 审计可追溯。

## 编码阶段与产出

| 阶段 | 操作 | 明确产出 | 检查与出口 |
|---|---|---|---|
| 9. 实现用户流程 | 依据已确认原型、实现矩阵和接口契约实现前端及必要后端 | 生产代码、样式和配置 | 当前用户流程可以在应用中实际操作 |
| 10. 开发自检 | 构建前后端，为新增或修改逻辑编写必要单元测试 | 单元测试代码、构建、类型检查和测试结果 | 代码级逻辑通过，接口实现可启动 |
| 11. 测试交接 | 交付原型、实现矩阵、用户流程、接口契约、影响范围和测试数据要求 | `development.md` 中的测试交接信息 | 测试 Agent 可以据此建立逐项 UI 覆盖 |
| 12. 开发完成 | 更新流程状态 | `ready_for_verification` 或 `blocked` | 原型、矩阵、契约、代码和开发自检结果一致 |
