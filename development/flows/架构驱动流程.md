# 架构驱动流程

## 何时选择

系统边界、模块职责、数据所有权、关键调用链或非功能指标是当前最大的开发不确定性。

局部功能不选本流程；从零开始也只有整体结构需要先决定时才选择。

## 进入输入

- 已确认的系统目标、范围和验收标准
- 业务与技术约束
- 现有系统、部署和运行事实；改造现有系统时

## 编码前阶段与产出

| 阶段 | 操作 | 明确产出 | 检查与出口 |
|---|---|---|---|
| 1. 建立约束基线 | 调查现有系统、环境、外部依赖和硬约束 | `development.md` 中的现状、约束和不可改变行为 | 关键结论有现有实现或运行事实支持 |
| 2. 确定系统边界 | 明确系统负责和不负责什么 | 系统边界及外部关系 | 需求均有归属，范围外内容已排除 |
| 3. 划分模块职责 | 以最少模块分配职责和依赖 | 模块职责及依赖关系 | 职责无明显重叠，不存在循环依赖设计 |
| 4. 明确数据所有权 | 为关键数据确定唯一所有者和访问方式 | 数据所有权和跨边界访问规则 | 没有多个模块同时直接控制同一数据 |
| 5. 走通关键链路 | 描述关键请求、事件和失败处理 | 关键调用链和失败链路 | 正常与失败路径都能闭合 |
| 6. 定义非功能指标 | 将性能、安全、可用性要求改写为可测阈值 | 指标、负载条件和通过阈值 | 指标能够通过工具实际测量 |
| 7. 验证高风险假设 | 对未知技术点运行最小实验 | 实验脚本、原始结果和结论 | 关键架构不依赖未经验证的假设 |
| 8. 记录关键决策 | 仅记录重要且难以逆转的取舍 | 必要的架构决策记录 | 决策包含依据、取舍和撤销条件 |
| 9. 拆执行单元 | 拆成功能切片，判断保留为子流程还是升级为独立子 Loop，并选择开发流程 | 子流程/子 Loop、依赖、范围、集成点和流程选择 | 每个单元可独立恢复和验证；超过上下文或可独立交付的切片已升级为子 Loop |

图、表和路线默认合并在 `development.md` 中，实验脚本和工具结果保留为实际产物。

## 编码前确认

```text
边界、职责和数据所有权明确
+ 关键正常和失败链路闭合
+ 非功能指标可测
+ 高风险假设已有证据
+ 子流程和集成点明确
→ 允许子流程进入编码
```

## 编码阶段与产出

| 阶段 | 操作 | 明确产出 | 检查与出口 |
|---|---|---|---|
| 10. 实现功能切片 | 每个子流程进入对应的具体开发流程 | 可运行的生产代码切片 | 切片能够独立运行或到达约定集成点 |
| 11. 开发自检 | 构建受影响模块，为关键模块逻辑编写必要单元测试 | 构建、静态检查和单元测试结果 | 模块能够编译并满足代码级约束 |
| 12. 测试交接 | 交付模块边界、关键链路、指标阈值、影响范围和环境要求 | `development.md` 中的测试交接信息 | 测试 Agent 可以据此设计集成和指标验证 |
| 13. 开发完成 | 更新架构流程状态 | `ready_for_verification` 或 `blocked` 及子流程引用 | 所有进入测试的切片已经完成开发自检 |
