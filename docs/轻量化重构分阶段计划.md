# Workloop 轻量化重构分阶段计划

## 1. 改造目标

Workloop 不再以“覆盖所有开发治理场景”为默认目标，而以最小认知闭环为核心：

> 用最少的固定产物，让 Agent 明确理解了什么、依据什么行动、如何证明结果，以及失败后修正了哪项认知。

重构保留五类有效思想：

- 假设与知识状态管理；
- 语义验证；
- 流程状态与认知状态分离；
- 错误记忆；
- 认知一致性校验。

重构主动移除默认存在的重治理机制：多档流程、全生命周期 Skill 集、全量 Flow 路由、控制快照、人工 Gate 兼容层、历史 Loop 迁移和大规模参考资料复制。

## 2. 目标形态

```text
用户需求
  → 理解：意图、边界、验收、关键认知
  → 计划：风险义务、可独立工作包、共享边界
  → 执行：一次只执行一个工作包
  → 验证：验收、认知、契约和实现的一致性
  → 学习：失败修正认知并形成可复验预防措施
```

系统只有一套最小骨架，不提供 Lite、Standard、Strict 三套平行流程。风险只会增加当前任务的验证义务，不会切换整套流程。

## 3. 固定产物

每个任务位于 `.workloop/tasks/<task-id>/`，固定维护四个 JSON 产物：

| 文件 | 信息责任 | 是否始终存在 |
|---|---|---:|
| `brief.json` | 意图、范围、验收、认知项、风险义务、任务状态 | 是 |
| `plan.json` | 可独立工作包、依赖、输入输出、共享边界契约 | 是 |
| `evidence.json` | 验收、认知、契约、失败复验的证据索引 | 是 |
| `failures.json` | 失败原因、错误认知、预防措施及复验证据 | 是，可为空 |

选择 JSON 而不是 YAML，是为了第一阶段不引入解析依赖、Schema 运行时或 vendor 包。JSON 本身仍适合 AI 读取，也避免 YAML 隐式类型和解析器差异。若真实使用证明 YAML 的可编辑性收益更高，再在插件阶段增加双格式适配。

## 4. 最小状态机

任务主状态：

```text
draft → ready → executing → verifying → done
          ↑          ↓           ↓
          └──── revise ←─────────┘
                   ↕
                blocked
```

认知项状态独立存在：

```text
unverified | confirmed | rejected | conflicted | resolved
```

任务状态回答“做到哪里”，认知状态回答“知道到什么程度”。认知项通过 `blocks` 声明在哪个目标状态前必须解决，避免所有未知项都在需求阶段阻断。

## 5. 分阶段实施

### 阶段 A：最小协议与单一 Skill（本分支首个交付）

产出：

- 最小认知协议；
- 单一 `workloop` Skill；
- 四个产物模板；
- 一个无第三方依赖的控制脚本；
- 工作项投影；
- 核心正向与负向测试。

验收：

- Skill 主体保持短小，阶段细节按需读取；
- 单 Agent 可按工作包顺序执行；
- Subagent 可只接收一个工作项投影；
- `done` 前能判定未覆盖验收、未解决关键认知、契约漏验和失败未学习；
- 不依赖旧 AgentLoop 运行时。

### 阶段 B：真实任务校准

选择小修改、普通功能、前后端共享接口、失败重试四类真实任务，观察：

- 哪些字段经常为空或只是形式负担；
- 哪些一致性规则容易误判；
- 工作项投影能否支持新会话恢复；
- 哪些规则仅靠 Skill 容易被遗漏或绕过；
- 哪些风险义务应自动推导。

本阶段只调整协议，不新增控制层。

### 阶段 C：严格插件控制

仅将阶段 B 证明稳定且适合机器判断的规则固化：

- JSON Schema 与语义校验；
- 合法状态转换；
- ID 与引用完整性；
- 验收覆盖；
- 阻塞认知解决；
- 契约变更导致旧证据失效；
- failed Evidence 必须对应错误记忆；
- 未满足完成条件时禁止进入 `done`。

插件不尝试自动理解任意业务代码语义，只检查结构化语义验证是否完整、当前、可追溯。

### 阶段 D：替换旧插件与清理

当新闭环通过阶段 B/C 验收后：

- 将 Marketplace 默认入口切到新 `workloop`；
- 删除旧 `development-process-agentloop` 插件及重复参考快照；
- 删除旧 Loop 示例、控制快照和迁移逻辑；
- 保留一份旧版能力到新版义务的映射文档；
- 通过 Git 历史访问旧实现，不在主分支保留兼容副本。

## 6. 明确不做

- 不为需求、开发、验证、恢复各建一个 Skill；
- 不默认生成接口文档、质量指标或失败卡；
- 不因任务规模切换整套流程；
- 不把所有历史材料注入当前 Agent；
- 不把“Agent 声称通过”视为证据；
- 不在协议未稳定前重建复杂 Hook、快照或迁移系统。

## 7. 成功指标

第一阶段以这些指标判断是否真的变轻：

- 核心 Skill 不超过 200 行；
- 默认任务只有四个小型产物；
- 当前工作包投影不包含无关工作包正文；
- 控制脚本只依赖 Python 标准库；
- 普通任务不创建共享契约、量化指标或失败明细；
- 每个新增字段都能对应一个明确的阻断判断或恢复用途。
