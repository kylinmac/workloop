# AgentLoop 路由与阶段交接协议

## 目的

本协议规定如何选择执行模式、开发流程和测试执行器，以及阶段之间交付什么。所有结构化结果使用[产物与目录协议](产物与目录协议.md)中的规范字段，不创建独立交接报告。

## 总路由

```text
检查状态、需求版本、Git 和输入
→ 选择 execution_profile
→ 判断单 Loop、复合子流程或父子 Loop
→ 查找并复用已有产物和可复用测试流程
→ 选择一个主开发流程
→ 只组合被实际触发的开发子流程
→ 为每个执行单元形成独立测试交接
→ 通过入口检查后推进状态
```

需求主要类型用于补充核对和风险提示，不能直接替代开发流程选择。

## 执行模式路由

```text
满足全部 trivial 资格条件
→ execution_profile: trivial

一个上下文内可完成，只有一个交付单元
→ execution_profile: standard

同一需求包含多个有依赖、可独立开发验证的小流程
→ execution_profile: composite

可独立确认、交付、回滚或并行，或内容超过单次上下文
→ epic 父 Loop + delivery 子 Loop
```

`trivial` 资格条件和升级规则由产物协议统一定义。模式判断是复杂度和调度决策，不改变需求分类。

## 稳定路由 ID

### 开发流程

| ID | 流程 |
|---|---|
| `quick-change` | 快速变更流程 |
| `product-prototype` | 产品原型驱动流程 |
| `business-process` | 业务流程驱动流程 |
| `data-contract` | 数据与契约驱动流程 |
| `domain-model` | 领域模型驱动流程 |
| `architecture` | 架构驱动流程 |
| `root-cause` | 根因驱动修复流程 |
| `migration-compatibility` | 迁移与兼容驱动流程 |
| `technical-validation` | 技术验证驱动流程 |

### 测试执行器

| ID | 执行器 |
|---|---|
| `code` | 代码流程验证 |
| `ui` | UI 流程验证 |
| `command` | 命令与实验流程验证 |

## 开发流程路由

### 输入

- 当前 `loop.yaml`
- 当前版本需求记录
- 已确认需求原型；存在时
- 事实与现状证据
- 项目代码、测试和 Git 状态
- 已有开发产物和 `.agentloop/flows/`

### 选择顺序

```text
已确认缺陷且需要定位共同根因
→ root-cause

存在新旧转换、兼容窗口或回滚问题
→ migration-compatibility

关键技术能否成立缺少运行证据
→ technical-validation

系统边界、模块职责或非功能指标最不确定
→ architecture

页面、交互或用户路径最不确定
→ product-prototype

角色、步骤、状态、异常或补偿最不确定
→ business-process

数据结构、接口契约或系统集成最不确定
→ data-contract

业务概念、规则或不变量最不确定
→ domain-model

范围小、路径明确、影响可控
→ quick-change
```

一个执行单元只能有一个主开发流程。其他流程作为 `supporting_flows`，只执行被触发的编码前阶段，不重复完整主流程。`supporting_flows` 是方法组合，不是 `loop.yaml.subflows` 中的逻辑执行单元。

## 拆分与调度

### 同一 Loop 的子流程

适用于共享同一已确认需求、但能够分别开发和验证的单元。每个子流程必须在 `loop.yaml.subflows` 中声明：

- 状态和依赖
- 主开发流程
- 修改范围
- Git 分支、worktree 和检查点
- 自己的测试交接
- 验证往返次数

依赖未通过时不得启动。默认顺序执行；只有范围不冲突、环境不共享且可以独立回滚时才并行。

### 父子 Loop

架构流程拆出的功能切片出现以下任一条件时升级为子 Loop：

- 可独立确认或交付
- 不同负责人、仓库、工作树或发布节奏
- 需要独立并行或回滚
- 单个切片已超过一次上下文可安全恢复的范围

父 Loop 只保存总体需求、架构边界、依赖和聚合状态；子 Loop 保存自身范围内的完整需求引用、开发和测试证据。

## 测试流程检索与路由

先用开发交接的影响范围检索 `.agentloop/flows/*.yaml` 的 `covers`：

```text
接口、数据库对象或业务状态精确匹配
→ 优先候选

路径 glob 匹配
→ 次级候选

标签匹配
→ 补充候选
```

多个候选无法确定时，路由置信度为 `low`，不得靠名称猜测。

```text
已有可复用测试流程定义
→ 复用；确认预期保持还是按需求改变

没有流程覆盖新增独立业务路径
→ 新增可复用测试流程定义

代码、接口、数据或状态能够 Assert
→ code

必须经过真实页面操作判断用户结果
→ ui

必须运行迁移、负载、故障或实验程序
→ command
```

一个可复用测试流程默认使用一个主执行器，单个执行器无法覆盖验收结果时才组合。回归不是新执行器，也不创建“回归流程”副本。

## 规范路由结构

路由只写入以下嵌套结构：

```yaml
routing:
  status: decided
  decided_at: "2026-07-30T10:00:00+08:00"
  decided_by: development-agent
  confidence: high
  development:
    main_flow: product-prototype
    reason: 页面交互和用户路径是主要不确定性
    supporting_flows: [data-contract]
    required_outputs: [prototype, openapi, database-migration]
  verification:
    reused_flows: [user-login]
    new_flows: [refund-application]
    executors:
      refund-application: [ui, code]
```

禁止使用 `routing.development_flow`、`routing.subflows` 等平铺别名。`reason` 必须引用实际需求、现状或风险。

## 路由置信度和审批

```text
high
→ 一个选择明显覆盖主要不确定性
→ 按项目审批策略自动决定

medium
→ 主流程明确，仅有条件子流程
→ 自动选择主流程并记录触发条件

low
→ 不同选择会明显改变范围、产物或成本
→ 保持当前状态并请求有效审批事件
```

置信度低时不得同时选择多个主流程规避决策。审批方式遵守 `project.yaml.approval.routing_confirmation`。

## 需求到开发交接

允许交接：

```text
state == ready_for_development
+ requirement_version 与需求记录一致
+ requirement_confirmation Gate 已通过
+ 必要需求原型已确认
+ 阻塞问题为零
+ Git baseline 已建立
```

交付内容：

- 目标、范围、非目标和验收标准
- 事实与现状证据
- 主要类型、特征标签和执行模式
- 业务规则、关键约束和不变行为
- 原型决定和引用
- 允许进入开发的未解决问题

开发 Agent 先检查输入，再进入 `development_preparing`；复合 Loop 完成拆分后进入 `orchestrating`。

## 开发到测试交接

普通 Loop 写入顶层 `verification_handoff`；复合 Loop 写入当前 `subflows[].verification_handoff`，结构一致：

```yaml
verification_handoff:
  requirement_version: 1
  code_commit: "<sha>"
  implemented_flows: [refund-application]
  changed_files: []
  changed_interfaces: []
  changed_data: []
  changed_states: []
  affected_existing_flows: []
  invariant_behaviors: []
  suggested_checks: []
  test_accounts: []
  test_data: []
  environment_requirements: []
  feature_flags: []
  known_limitations: []
```

允许交接：

```text
生产代码已形成 Git 提交
+ 构建、静态检查和必要单元测试通过
+ 契约、Schema 和脚本可解析
+ 交接字段完整
```

交接后进入 `ready_for_verification`；复合 Loop 只更新当前子流程状态，父状态保持 `orchestrating`。

## 测试失败交回

```text
实现错误
→ 当前普通 Loop 或子流程回到 developing

需求、范围或预期错误
→ 整体回到 clarifying

测试代码、数据或环境错误
→ 保持 verifying

外部依赖不可用
→ blocked，并记录 resume_state
```

最低失败交接；普通 Loop 写入顶层，复合 Loop 写入当前 `subflows[].failure_handoff`：

```yaml
failure_handoff:
  flow_id:
  subflow_id:
  executor:
  code_commit:
  expected:
  actual:
  failed_assertion:
  evidence:
  suspected_area:
  affected_flows:
  rerun_scope:
```

测试 Agent 提供事实和证据，不指定未经证明的修复方案。

## 测试通过到完成

```text
普通 Loop 所有必需测试 passed
→ verified

复合 Loop 当前子流程测试 passed
→ 子流程 passed
→ 按聚合规则决定父状态

project.yaml.approval.completion.mode == automatic_after_verified
→ verified → done

project.yaml.approval.completion.mode == human_acceptance
→ 有效人工验收事件
→ verified → done
```

人工验收不能改写已确认需求；改变预期必须增加需求版本并退回 `clarifying`。

## 交接拒绝

出现以下任一情况时保持原状态并记录缺失项和负责人：

- 状态或需求版本不一致
- 必需文件或 Git 提交不存在
- 验收标准不可执行
- 账号、数据或环境缺失
- 交接属于错误子流程
- 产物已 `stale`
- 已知阻塞未处理

## 更新顺序

```text
发送方完成实际产物和出口检查
→ 创建 Git 检查点
→ 写入当前执行单元的交接
→ 接收方检查并接受
→ 更新子流程或主状态和 transition
```
