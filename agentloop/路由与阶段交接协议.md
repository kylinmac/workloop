# AgentLoop 路由与阶段交接协议

## 目的

本协议规定如何选择执行模式、开发流程和测试执行器，以及阶段之间交付什么。所有结构化结果使用[产物与目录协议](产物与目录协议.md)中的规范字段，不创建独立交接报告。

## 总路由

```text
draft：根据已知信息形成 provisional execution_profile
→ clarifying：核对事实、范围，并为每项验收建立稳定 ID、独立来源和可观察结果
→ 确认 execution_profile
→ 检查状态、需求版本、Git 和输入
→ 判断单 Loop、复合子流程或父子 Loop
→ 查找并复用已有产物和可复用测试流程
→ 选择一个主开发流程
→ 只组合被实际触发的 supporting_flows
→ 建立“验收义务→实现→契约→Gate→Evidence→恢复”控制闭环
→ 为每个执行单元形成独立测试交接
→ 通过入口检查后推进状态
```

需求主要类型用于补充核对和风险提示，不能直接替代开发流程选择。

## 执行模式路由

```text
满足全部 trivial 资格条件
→ execution_profile.level: trivial

一个上下文内可完成，只有一个交付单元
→ execution_profile.level: standard

同一需求包含多个有依赖、可独立开发验证的开发切片
→ execution_profile.level: composite

可独立确认、交付、回滚或并行，或当前单元无法仅加载需求、开发记录和声明范围安全恢复
→ epic 父 Loop + delivery 子 Loop
```

`draft` 中的判断为 `provisional`；需求确认 Gate 前必须重新判断并设为 `confirmed`。`trivial` 资格条件和升级规则由产物协议统一定义。模式判断是复杂度和调度决策，不改变需求分类。

复杂需求只允许以下两种结构：

| 结构 | 使用条件 | 主状态 |
|---|---|---|
| 一个 Loop + 多个 `subflows` | 共享同一需求确认、负责人、仓库和整体交付；切片可独立开发验证 | 父状态始终 `orchestrating`，切片各走自己的闭环 |
| 一个 epic 父 Loop + 多个 delivery 子 Loop | 切片可独立确认、交付、回滚、并行，或无法只加载当前单元安全恢复 | 每个子 Loop 独立走完整主状态，父 Loop 形成集成基线并聚合 |

不得把两种结构混在同一层：`subflows` 不是子 Loop，子 Loop 也不复制为 `subflows`。标准 Loop 只有全部开发完成后才进入 `ready_for_verification`；复合 Loop 永不因为第一个切片完成而改变父状态。

复合 Loop 的 `routing.development.main_flow` 负责总体拆分和共同约束；每个 `subflows[].main_flow` 负责该切片的编码前准备，两者可以不同。

拆分示例：

```text
standard
→ “给退款接口增加一个必须按顺序完成的校验和落库步骤”
→ 步骤不能独立交付验证，保留一个 Loop

composite
→ “退款申请、支付回退、库存返还可分别开发验证，最后需要订单状态集成”
→ 一个复合 Loop + 三个 subflows + integration_verification

错误拆分
→ 按 controller / service / repository 技术层拆三个 subflows
→ 各层没有独立业务结果，不允许这样拆
```

## 稳定路由 ID

### 开发流程

| ID | 流程 |
|---|---|
| `quick-change` | 快速变更流程 |
| `product-prototype` | 产品原型驱动流程 |
| `business-process` | 业务流程驱动流程 |
| `data-contract` | 数据与契约驱动流程 |
| `domain-model` | 领域模型驱动流程 |
| `architecture` | 架构驱动流程 |
| `root-cause` | 根因驱动修复流程 |
| `migration-compatibility` | 迁移与兼容驱动流程 |
| `technical-validation` | 技术验证驱动流程 |

### 测试执行器

| ID | 执行器 |
|---|---|
| `code` | 代码流程验证 |
| `ui` | UI 流程验证 |
| `command` | 命令与实验流程验证 |

## 开发流程路由

### 输入

- 当前 `loop.yaml`
- 当前版本需求记录
- 已确认需求原型；存在时
- 事实与现状证据
- 项目代码、测试和 Git 状态
- 已有开发产物和 `.agentloop/flows/`

### 选择顺序

```text
已确认缺陷且需要定位共同根因
→ root-cause

存在新旧转换、兼容窗口或回滚问题
→ migration-compatibility

关键技术能否成立缺少运行证据
→ technical-validation

系统边界、模块职责或非功能指标最不确定
→ architecture

页面、交互或用户路径最不确定
→ product-prototype

角色、步骤、状态、异常或补偿最不确定
→ business-process

数据结构、接口契约或系统集成最不确定
→ data-contract

业务概念、规则或不变量最不确定
→ domain-model

范围小、路径明确、影响可控
→ quick-change
```

一个执行单元只能有一个主开发流程。其他流程作为 `supporting_flows`，只执行被触发的编码前阶段，不重复完整主流程。`supporting_flows` 是方法组合，不是 `loop.yaml.subflows` 中的逻辑执行单元。

## 拆分与调度

### 同一 Loop 的子流程

适用于共享同一已确认需求、但能够分别开发和验证的单元。每个子流程必须在 `loop.yaml.subflows` 中声明：

- 状态和依赖
- 主开发流程
- 修改范围
- Git 分支、worktree 和检查点
- 自己的 `targeted/flow` 验证策略、流程和执行器
- 自己的测试交接
- 验证往返次数

依赖未通过时不得启动。默认顺序执行；只有范围不冲突、环境不共享且可以独立回滚时才并行。

协调者必须在拆分完成、进入 `orchestrating` 前写入 `integration_verification.required: true/false` 和理由；字段不得依赖默认值。开发中发现新跨切片关系时只能及时升级为 `true`，不能静默保留 `false`。

### 父子 Loop

架构流程拆出的功能切片出现以下任一条件时升级为子 Loop：

- 可独立确认或交付
- 不同负责人、仓库、工作树或发布节奏
- 需要独立并行或回滚
- 恢复单个切片时无法仅加载其需求、开发记录和声明代码范围

父 Loop 只保存总体需求、架构边界、依赖和聚合状态；子 Loop 保存自身范围内的完整需求引用、开发和测试证据。

创建 delivery 子 Loop 时，协调者必须比较父子范围和验收：

```text
完全由父确认需求派生
→ requirement_confirmation.mode: inherited_from_parent
→ 记录父审批引用、范围子集和验收子集检查

新增范围、验收、规则、约束或风险
→ 不得继承
→ 子 Loop 独立执行需求确认 Gate
```

## 测试流程检索与路由

先选择验证策略：

```text
trivial
+ 单一确定结果
+ development.main_flow == quick-change
+ 无接口、数据、状态、权限、安全、迁移和外部集成风险
+ 可以直接观察最终结果
→ self_check

需要验证修改及相邻不变行为，但已有流程或定向检查可覆盖
→ targeted

新增独立业务路径，或涉及跨模块、状态、数据、权限、迁移、兼容和高风险行为
→ flow
```

`self_check` 只允许 `trivial`，并必须通过 `project.yaml.verification_policy.self_check_forbidden_tags` 检查；任一条件不满足立即升级，不得由 Agent 自行豁免。

`targeted/flow` 再用开发交接的影响范围检索 `.agentloop/flows/*.yaml` 的 `covers`：

```text
接口、数据库对象或业务状态精确匹配
→ 优先候选

路径 glob 匹配
→ 次级候选

标签匹配
→ 补充候选
```

多个候选无法确定时，路由置信度为 `low`，不得靠名称猜测。

```text
已有可复用测试流程定义
→ 复用；确认预期保持还是按需求改变

没有流程覆盖新增独立业务路径
→ 新增可复用测试流程定义

代码、接口、数据或状态能够 Assert
→ code

必须经过真实页面操作判断用户结果
→ ui

必须运行迁移、负载、故障或实验程序
→ command
```

一个可复用测试流程默认使用一个主执行器，单个执行器无法覆盖验收结果时才组合。回归不是新执行器，也不创建“回归流程”副本。主要类型为“技术研究”时，技术验证产生的实验脚本、初始结果和决策记录作为开发交付，再由 `command` 执行器复跑关键实验并验证阈值；通过后可以正常进入 `verified`，不要求继续实现产品功能。

## 规范路由结构

路由只写入以下嵌套结构：

```yaml
routing:
  status: decided
  decided_at: "2026-07-30T10:00:00+08:00"
  decided_by: development-agent
  confidence: high
  development:
    main_flow: product-prototype
    reason: 页面交互和用户路径是主要不确定性
    supporting_flows: [data-contract]
    required_outputs: [prototype, openapi, database-migration]
  verification:
    policy: flow
    reason: 新增独立退款路径且涉及状态与幂等
    reused_flows: [user-login]
    new_flows: [refund-application]
    executors:
      refund-application: [ui, code]
```

禁止使用 `routing.development_flow`、`routing.subflows` 等平铺别名。`reason` 必须引用实际需求、现状或风险。

普通 Loop 直接执行 `routing.verification`。复合 Loop 把它作为默认策略和总体影响索引，再为每个 `subflows[].verification` 写入实际执行路由；最终跨切片路由写入 `integration_verification`。

## 路由置信度和审批

路由首先声明当前最大的风险驱动，而不是先挑一个熟悉的流程再补理由。`routing.risk_driver` 必须记录风险类别、具体陈述、事实依据和严重度；主流程必须与风险类别对应。影响路由的 `unverified` 假设会阻止路由，直到假设被证据确认或否定。

执行档位资格与验证降档不得只写自然语言理由。新版 Loop 的 `execution_profile.qualifications` 记录单一交付单元、范围已知、低风险、结果可直接观察和并发事实；trivial/self_check 只有全部资格满足且没有项目禁止标签时可用，任一条件失败自动拒绝该路由并要求升级。

```text
high
→ 一个选择明显覆盖主要不确定性
→ 按项目审批策略自动决定

medium
→ 主流程明确，仅有条件 supporting_flows
→ 自动选择主流程并记录触发条件

low
→ 不同选择会明显改变范围、产物或成本
→ `gates.routing_confirmation` 设为 pending
→ 保持当前状态并请求有效 Gate 事件
```

置信度低时不得同时选择多个主流程规避决策。审批方式遵守 `project.yaml.approval.routing_confirmation`，结果写入 `loop.yaml.gates.routing_confirmation`。

## 需求到开发交接

允许交接：

```text
state == ready_for_development
+ requirement_version 与需求记录一致
+ requirement_confirmation Gate 已通过
+ execution_profile.status == confirmed
+ 每项验收有稳定 ID、独立来源和可观察结果
+ 必要需求原型已确认
+ integration_data 已显式决定；启用时前端路由、后端接口、数据库对象和验证 flow 完整
+ 阻塞问题为零
+ Git baseline 已建立
```

交付内容：

- 目标、范围、非目标，以及带稳定 ID、来源和可观察结果的验收标准
- 事实与现状证据
- 主要类型、特征标签和执行模式
- 业务规则、关键约束和不变行为
- 原型决定和引用
- 前后端真实数据链路决定及范围
- 允许进入开发的未解决问题

开发 Agent 先检查输入，再进入 `development_preparing`；复合 Loop 完成拆分后进入 `orchestrating`。

选择 `product-prototype` 时，控制程序自动登记原型实现矩阵、行为清单和用户流程切片；存在服务端数据或写操作时还必须登记 API 契约与数据模型/复用声明。独立从原型提取的页面、区域、控件和交互集合与这些产物精确比对通过前，不得开始编码。

## 开发到测试交接

普通 Loop 使用 `routing.verification`；复合 Loop 先把每个切片的具体策略、流程和执行器写入 `subflows[].verification`。策略为 `targeted/flow` 时，普通 Loop 写入顶层 `verification_handoff`，复合 Loop 写入当前 `subflows[].verification_handoff`，结构一致：

```yaml
verification_handoff:
  requirement_version: 1
  code_commit: "<sha>"
  scope: "<loop-or-subflow-id>"
  acceptance_ids: []
  implemented_flows: [refund-application]
  changed_files: []
  changed_interfaces: []
  changed_data: []
  changed_states: []
  affected_existing_flows: []
  invariant_behaviors: []
  suggested_checks: []
  test_accounts: []
  test_data: []
  environment_requirements: []
  feature_flags: []
  known_limitations: []
```

允许交接：

```text
生产代码已形成 Git 提交
+ 构建、静态检查和必要单元测试通过
+ 契约、Schema 和脚本可解析
+ 验收义务、实现、契约和验证步骤映射完整
+ loop、需求版本、范围、flow/check 和 tested commit 可组成精确验证身份
+ 交接字段完整
```

交接后进入 `ready_for_verification`；复合 Loop 只更新当前子流程状态，父状态保持 `orchestrating`。

`policy: self_check` 不建立测试交接。开发 Agent 运行直接检查，把命令、实际结果和验收结论写入 `work.md`；全部通过后直接进入 `verified`。

UI flow 的 `automation.path` 必须是项目内存在的可执行测试或脚本；`.md` 报告只能进入 evidence。包含 `visual` 或高保真原型时，交接必须带原型引用、固定 viewport、对比方式、允许差异、通过标准和逐项 coverage。

启用 `integration_data` 时，交接还必须指向含 `data_lineage` check 的 flow，并说明测试数据库隔离方式、数据生成入口和唯一 sentinel 的断言位置。测试必须从数据库生成数据开始，经过真实 API 到真实页面，不能用 mock 或静态展示替代。

## 跨切片集成交接

复合或 epic Loop 的切片全部达到依赖条件后，Loop 协调者检查 `integration_verification`：

```text
required == false
→ state: not_required
→ composite 或同仓库 epic 仍须完成交付单元合并和合并后检查
→ git.integration.status: verified 后才可聚合

required == true
→ composite 或同仓库 epic 先完成交付单元合并和合并后检查
→ 在 integration_verification.handoff 写入精确 code_commit、切片提交、接口、数据、状态和环境
→ 跨仓库 epic 写入各子 Loop 的已验证交付提交和环境
→ state: ready_for_verification
→ 测试 Agent 执行集成流程
→ passed 后才允许父 Loop verified
```

`handoff.code_commit` 必须等于实际测试的集成提交；代码变化后原证据失效。父级聚合时按当前需求版本、当前集成提交和各子流程范围选择 active Evidence，并重新核对验收义务覆盖，不能只读取子流程状态。集成失败写入 `integration_verification.failure_handoff.affected_subflows`。能够定位时只退回受影响切片；无法定位时父 Loop 进入 `blocked`，不得把全部切片无差别重做。

## 测试失败交回

```text
实现错误
→ 当前普通 Loop 或子流程回到 developing

需求、范围或预期错误
→ 整体回到 clarifying

测试代码、数据或环境错误
→ 保持 verifying

外部依赖不可用
→ blocked，并记录 resume_state
```

最低失败交接；普通 Loop 写入顶层，复合 Loop 写入当前 `subflows[].failure_handoff`：

```yaml
failure_handoff:
  flow_id:
  subflow_id:
  executor:
  code_commit:
  expected:
  actual:
  failed_assertion:
  evidence:
  suspected_area:
  affected_flows:
  rerun_scope:
```

测试 Agent 提供事实和证据，不指定未经证明的修复方案。

## 测试通过到完成

```text
普通 Loop 所有必需测试 passed
→ verified

普通 Loop policy == self_check 且直接检查满足全部验收
→ developing → verified

复合 Loop 当前子流程测试 passed
→ 子流程 passed
→ 所有切片通过后按需执行 integration_verification
→ 按聚合规则决定父状态

project.yaml.approval.completion.mode == automatic_after_verified
→ verified → done

project.yaml.approval.completion.mode == human_acceptance
→ 有效人工验收事件
→ verified → done
```

人工验收不能改写已确认需求；改变预期必须增加需求版本并退回 `clarifying`。

## 交接拒绝

出现以下任一情况时保持原状态并记录缺失项和负责人：

- 状态或需求版本不一致
- 必需文件或 Git 提交不存在
- 验收标准不可执行
- 账号、数据或环境缺失
- 交接属于错误子流程
- 产物已 `stale`
- Evidence 与当前验证身份不匹配，或已被替代
- 已知阻塞未处理

## 更新顺序

```text
发送方完成实际产物和出口检查
→ 创建 Git 检查点
→ 写入当前执行单元的交接
→ 接收方检查并接受
→ 将同一验证身份的旧 Evidence 标记为 superseded
→ 更新子流程或主状态和 transition
```
