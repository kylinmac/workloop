# AgentLoop 设计原则

## 目的

AgentLoop 是开发控制系统，不只是流程说明。它必须同时适配简单小改动和复杂大型需求，并保证“文档要求、状态许可、真实执行和最终结论”一致。

所有需求、开发、验证、编排、恢复和插件实现都遵守本原则。具体状态和字段分别由状态机、产物协议、交接协议及执行恢复协议定义。

## 1. 每条强制规则必须形成控制闭环

文档中的每个“必须、禁止、只有……才允许”都必须能回答：

```text
规则依据来自哪里
→ 由什么结构或 Schema 表达
→ 在哪个状态转换或 Gate 阻止违规推进
→ 由什么真实执行产生证据
→ 哪个回归样例证明门禁有效
→ 失败后从哪里恢复
```

能够自动检查的规则必须由控制程序检查。不能自动检查的规则必须明确人工 Gate、责任人和确认对象。仅有提示语或依赖 Agent 自觉不构成强制规则。

## 2. 验收基线必须独立于实现和测试声明

进入路由和实现前，必须把会改变范围、验收、实现或验证的假设写入 `assumptions`。未验证的阻塞假设不得被自然语言理由掩盖；确认或否定假设必须附证据。存在多个可行选项时，使用 `decision_records` 保存候选、选择、依据和排除理由，不能只保存最终结论。

事实、未知项和来源冲突不得混写在理由文本中。`knowledge_state` 分别保存 `known`、`unknowns` 和 `conflicts`；每项声明影响阶段。未解决且会影响后续工作的未知项或冲突必须在对应状态转换前阻止推进，解决时必须保存结论和证据。

不能让同一份遗漏同时复制到需求矩阵、实现、自动化和 Evidence 后形成自证闭环。

```text
独立事实源或已确认需求
→ 可执行验收义务
→ 实现映射
→ 验证映射
→ 实际证据
```

实现映射与验证映射都必须和独立基线做集合比较。原型源码、OpenAPI、数据库约束、状态规则、外部规范和用户确认记录都可以成为独立基线；Agent 自己填写的“已完成列表”不能单独成为基线。

## 3. 先定义验证身份，再消费 Evidence

任何状态推进或聚合都先确定验证身份：

```text
loop_id
+ requirement_version
+ loop/subflow/child scope
+ flow_id 或 check_id
+ tested_commit
+ run identity
```

Evidence 只有与完整身份一致、状态为 active、执行结果有效时才可消费。新运行必须确定性地替代同一身份范围内的旧运行；父级不得用自己的提交验证子流程，也不得把不同检查能力的 Flow 混入同一 Gate。

## 4. 状态表示许可，不表示事实本身

`developing` 表示编码入口条件已通过，不表示实现正确；`passed/verified` 表示对应证据通过，不表示用户已经验收；父级 `orchestrating` 不授予子流程编码许可。

每个状态必须有：

- 入口契约：进入前必须存在并通过的事实、产物和 Gate。
- 允许操作：当前状态唯一允许推进的工作类型。
- 出口契约：离开时必须产生的实际产物、提交和证据。
- 失败契约：失败分类、失效范围和退回位置。
- 恢复契约：中断、重复执行或升级后如何重新建立入口事实。

## 5. 失败关闭，但恢复必须可达

无法证明满足条件时默认不推进。阻止推进的同时必须给出可执行恢复路径，禁止出现“需要恢复后才能生成恢复所需产物”的循环依赖。

新增 Gate 或必需产物时必须同时设计：

```text
新建正常路径
+ 验证失败路径
+ 修复重跑路径
+ completion 驳回路径
+ 旧版本升级与中断恢复路径
```

## 6. 追加历史，明确当前有效记录

需求版本、转换、Gate、提交和 Evidence 历史不得删除，但必须用 `active / stale / superseded` 等明确生命周期区分当前有效记录。追加日志不能依赖“调用方碰巧选择正确的一条”。

状态修改、Evidence 写入和集成 checkpoint 必须原子完成；重试必须幂等，失败不得留下半更新控制状态。

## 7. 复杂度只增加必要的协调，不复制闭环

三种执行档位共享同一套事实与证据原则：

| 档位 | 表达方式 | 不可省略 |
|---|---|---|
| `trivial` | 需求、义务映射和自检可合并在 `work.md` | 独立验收依据、真实检查、Git 提交和转换记录 |
| `standard` | 一个 Loop 顺序执行完整闭环 | 编码前入口、交接、提交绑定和 targeted/flow Evidence |
| `composite/epic` | 每个执行单元复用同一闭环，父级只增加依赖、集成和聚合 | 子单元独立许可、统一集成基线、父级语义重验 |

复杂需求不能按技术层机械拆分；简单需求不能为了形式生成空文档。

## 8. 验证必须包含正向、负向和持久结果

只证明页面打开、控件存在、命令退出码为零或 Agent 自报 passed，不足以证明业务完成。

验证按风险至少覆盖：

- 正常路径和最终结果。
- 关键分支、失败和无权限路径。
- 数据或状态写入后的 readback、刷新、重登和下游消费。
- 声明保持不变的相邻行为。
- 当前提交上的真实自动化执行和大于零的断言。

视觉、业务功能、数据链路、权限、安全、迁移和性能 Gate 相互独立；一个 Gate 通过不能补偿另一个 Gate 失败。

## 9. 协议变更必须先做影响与迁移设计

修改 AgentLoop 文档、Schema、控制程序或插件时，编码前必须列出：

```text
受影响状态与转换
+ 新旧字段和兼容策略
+ 当前与历史 Loop 的迁移路径
+ Evidence 失效和替代规则
+ 正常、负向、重跑、恢复、升级回归
```

每个独立缺陷按[AgentLoop 问题复盘规则](../rules/AgentLoop问题复盘规则.md)建立一份问题档案。重复出现的根因必须提升为本设计原则或通用规则，不能只继续追加事故特判。

## 10. 控制状态完整，模型上下文最小

完整 `loop.yaml`、转换历史、Gate 事件和 Evidence 是持久控制底账，不等于每轮都要注入模型上下文。控制程序必须先校验底账，再按当前状态和工作单元生成只读阶段投影。

每轮默认只加载：

```text
Loop 身份与当前状态
+ 当前阶段入口和出口所需字段
+ 当前验收映射或活动 Evidence 摘要
+ 一个阶段 Skill
```

需求阶段不得加载实现与 Evidence 历史；开发阶段不得加载 Gate 事件和旧验证记录；验证阶段不得加载无关分类细节；父级编排只加载子单元摘要，处理单个子流程时必须使用其独立投影。只有恢复或具体控制错误诊断才能读取完整底账。

强制规则应由 Schema、控制命令和 Gate 执行，不能为了让 Agent “记住”而重复写入所有阶段提示。阶段投影必须携带源文件摘要，保持可追溯但不得成为新的可写状态源。

## 统一判断

任何阶段准备推进时，按同一顺序判断：

```text
独立依据是否完整
→ 当前义务是否全部映射
→ 状态入口是否满足
→ 执行是否真实发生
→ Evidence 身份和生命周期是否有效
→ 负向与恢复路径是否已覆盖
→ 才允许推进
```
