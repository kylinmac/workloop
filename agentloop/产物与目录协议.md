# AgentLoop 产物与目录协议

## 目的

本协议是 AgentLoop 文件结构和字段的唯一正式定义。其他协议只引用这里的字段，不得另造同义字段。

本目录的 `schemas/*.schema.json` 是字段结构的机器可读投影，`examples/*.yaml` 是最小有效样例。Markdown 负责语义，Schema 负责字段、枚举和结构；两者冲突时不得运行，必须先修正协议并保持同步。

目标：

- 人和 Agent 能从项目目录恢复任务
- 同一信息只有一个正式来源
- 简单需求保持最小开销
- 复杂需求能够表达子流程、父子 Loop 和产物失效
- 代码、原型、契约、脚本和测试仍放在项目原有位置

## 术语

为避免“flow 文件”混用，统一使用：

| 术语 | 含义 | 正式位置 |
|---|---|---|
| 开发记录 | 编码前产物索引、实现记录和开发自检 | `development.md`；`trivial` 模式下为 `work.md` |
| 子流程 | 可独立开发和验证的逻辑执行单元 | `loop.yaml` 的 `subflows` |
| 辅助开发流程 | 主开发流程按需组合的编码前方法 | `routing.development.supporting_flows` |
| 可复用测试流程定义 | 可跨需求重复运行的步骤、预期和执行器 | `.agentloop/flows/<flow_id>.yaml` |
| 运行证据 | 某次真实测试或命令运行的结果索引 | `evidence.yaml` |

不得再使用“开发 flow 文件”或用 `flow.md` 表示可复用测试流程。

## 项目内标准目录

```text
<project_root>/
├── .agentloop/
│   ├── project.yaml
│   ├── schemas/                     # 运行引擎使用的 JSON Schema
│   ├── examples/                    # 通过 Schema 校验的最小样例
│   ├── locks/                       # 运行时锁，不提交 Git
│   ├── loops/
│   │   └── <loop_id>/
│   │       ├── loop.yaml
│   │       ├── requirement.md       # standard / composite
│   │       ├── development.md       # standard / composite
│   │       ├── work.md              # 仅 trivial，合并需求与开发记录
│   │       ├── evidence.yaml        # 有运行证据时创建
│   │       └── artifacts/           # 项目没有更合适位置时才创建
│   └── flows/
│       └── <flow_id>.yaml           # 可复用测试流程定义
├── <项目原有代码和测试目录>
└── <项目原有文档、契约和迁移目录>
```

`.agentloop/` 保存控制信息，不替代项目原有目录规范。

运行引擎可以内置本协议版本对应的 Schema，也可以复制到项目 `.agentloop/schemas/`；同一项目只能使用一个 `schema_version`。本流程库中的样例可运行 `python3 agentloop/validate_examples.py` 校验。

## 执行模式和最小文件

`execution_profile` 是入口复杂度和调度方式，不是需求类型：

| 模式 | 适用情况 | 最小 Loop 文件 |
|---|---|---|
| `trivial`（轻量路径） | 单一、小范围、高置信度变化 | `loop.yaml` + `work.md`；独立测试运行时才增加 `evidence.yaml` |
| `standard` | 一个 Loop 内完成的普通需求 | `loop.yaml` + `requirement.md` + `development.md`；有验证时增加 `evidence.yaml` |
| `composite`（多切片路径） | 包含多个独立子流程的需求 | 与 `standard` 相同，并在 `loop.yaml` 维护 `subflows` |

`loop_kind: epic` 的父 Loop 固定使用 `execution_profile.level: composite`，但用 `child_loops` 而不是 `subflows` 表达交付单元。`delivery + composite` 与 `epic + composite` 不得在同一层同时填充 `subflows` 和 `child_loops`。

`trivial` 只允许用于同时满足以下条件的需求：

```text
单一可观察变化
+ 修改位置和影响范围明确
+ 不新增或修改接口、表结构、状态机、权限、安全规则、迁移和外部集成
+ 不需要产品原型
+ 有可直接运行的已有检查或低成本验证
```

任一条件不满足，升级为 `standard`。出现多个可独立交付单元时，升级为 `composite` 或父子 Loop。

入口分流分两次完成：

```text
draft
→ 根据原始输入形成 provisional 档位
→ clarifying 按事实、范围和验收重新判断
→ 需求确认 Gate 前将档位设为 confirmed
```

档位未 `confirmed` 时不得进入开发。需求确认后发现低估复杂度但需求本身未变，可以只升级档位；发现范围或验收变化则必须增加需求版本并重新确认。不得在开发中自动降级以绕过检查。

项目首次接入时额外创建一次 `.agentloop/project.yaml`。只有新增了可长期复用的测试流程时，才创建 `.agentloop/flows/<flow_id>.yaml`。

## 单一事实来源

| 信息 | 唯一正式来源 |
|---|---|
| 状态、路由、审批、子流程、产物有效性和交接索引 | `loop.yaml` |
| 已确认需求、分类、验收标准和需求原型引用 | `requirement.md` 或 trivial 的 `work.md` |
| 开发流程选择、编码前产物和开发自检 | `development.md` 或 trivial 的 `work.md` |
| 测试运行、截图、报告和指标索引 | `evidence.yaml` |
| trivial 自检即验收的检查命令和实际结果 | `work.md` |
| 可复用测试步骤和预期 | `.agentloop/flows/<flow_id>.yaml` |
| 逐页原型实现矩阵 | `.agentloop/loops/<loop_id>/prototype-implementation-matrix.yaml` |
| 代码、单元测试、UI 自动化和脚本 | 项目原有目录 |
| OpenAPI、Schema、DDL 和迁移脚本 | 项目原有约定目录 |

`loop.yaml` 只保存结构化状态和索引，不复制大段正文。

## 标识规则

```text
loop_id     = al-<YYYYMMDD>-<三位序号>
subflow_id  = sf-<两位序号>-<短名称>
flow_id     = 稳定业务含义，如 refund-application
artifact_id = <loop_id>-<类型>-<序号>
```

ID 创建后不得因标题或内容变化而修改。`flow_id` 只使用小写字母、数字和短横线。

## `project.yaml`

项目配置只创建一次。最低结构：

```yaml
schema_version: 1
project_id: example-project
project_root: .

approval:
  requirement_confirmation:
    mode: manual
    minimum_confidence: high
    forbidden_tags: [security-compliance, data-change, external-integration, compatibility]
  routing_confirmation:
    mode: manual_on_low_confidence
  completion:
    mode: human_acceptance
  destructive_actions:
    mode: always_manual

verification_policy:
  defaults:
    trivial: self_check
    standard: targeted
    composite: flow
  self_check_forbidden_tags:
    [workflow-state, data-change, external-integration, security-compliance, compatibility]

execution:
  workdir: .
  default_timeout_seconds: 120
  max_verification_failure_roundtrips: 3
  concurrency: separate_worktree

git:
  slice_merge_strategy: merge_no_ff
  delivery_mode: verified_integration_branch   # verified_integration_branch | merge_to_target_after_verified

commands: {}                         # 根据项目事实填写；不预设语言或构建工具
paths:
  source: []
  tests: []
  protected: [".env", "secrets"]
```

允许的审批模式：

- `requirement_confirmation.mode`: `manual` 或 `auto_high_confidence`
- `routing_confirmation.mode`: `manual` 或 `manual_on_low_confidence`
- `completion.mode`: `human_acceptance` 或 `automatic_after_verified`
- `destructive_actions.mode`: 当前只允许 `always_manual`

`inherited_from_parent` 只用于 delivery 子 Loop 的运行时确认记录，不是项目默认审批模式；继承条件见状态机。

验证默认值也必须合法：`self_check` 只允许 `trivial`，且只在实际主流程为 `quick-change` 并通过全部禁止标签检查时生效；trivial 若改选其他主流程必须升级为 `targeted/flow`。`standard/composite` 只能配置为 `targeted` 或 `flow`。

当前 `slice_merge_strategy` 只定义 `merge_no_ff`。`delivery_mode` 为 `verified_integration_branch` 时交付已验证集成提交；为 `merge_to_target_after_verified` 时还必须按 Git 规则完成目标分支合并和复验。

没有显式配置时，审批、验证、执行和 Git 使用上述保守默认值，`commands` 使用空映射。Agent 不得自行放宽项目配置，也不得猜测项目命令。

命令使用参数数组，避免额外 Shell 解释。项目没有的命令直接省略；Agent 不得为填满配置安装新工具或猜测命令。配置不得保存令牌、密码和其他密钥。

`gates` 是运行态 Gate 的唯一正式来源。固定 Gate 为 `requirement_confirmation`、`routing_confirmation`、`completion` 和 `destructive_action`；非 Git 项目建立初始提交时按需增加 `repository_bootstrap`。所有 Gate 使用相同字段：

```yaml
gates:
  <gate_id>:
    gate_id: <gate_id>
    status: not_required             # not_required | pending | approved | rejected
    mode:
    event_id:
    subject_digest:
    operation_digest:               # 仅绑定具体操作时填写
```

每次决定追加到 `gate_events`，事件必须包含 `event_id/gate_id/decision/actor/source/source_event_id/requirement_version/subject_files/artifact_digest/at`。策略自动事件使用 `source: agent-policy`，仍由宿主分配唯一 `source_event_id`。当前 Gate 的 `event_id` 必须引用对应的最新有效事件；不得另建 `approval_events` 或 `approval.*` 别名。

默认审批配置是保守路径。希望 trivial 真正单轮完成的项目，应显式配置 `requirement_confirmation: auto_high_confidence` 和 `completion: automatic_after_verified`；禁止标签、低置信度、仓库初始化和破坏性操作仍停在人工 Gate。

`trivial` 模式的 `files` 只需：

```yaml
files:
  work: work.md
  evidence: evidence.yaml           # policy != self_check 且产生独立运行证据时才需要
```

`trivial` 升级为 `standard/composite` 时：

```text
从 work.md 拆出 requirement.md 和 development.md
→ 检查确认需求内容未被改写
→ 更新 loop.yaml.files 和 execution_profile
→ 重新路由验证策略；trivial → standard 时 self_check 必须升级为 targeted 或 flow
→ 在同一 Git 检查点删除 work.md
```

Git 历史保留旧记录，工作区只保留新的单一事实来源。

路径默认相对于当前 `loop.yaml`；项目文件路径相对于 `project_root`，禁止使用 `..` 跳出项目。

`trivial/standard` 的 `git.branch/worktree` 是本 Loop 实际工作位置。没有其他活动 Loop、范围不冲突、目标分支不受保护且用户已有修改不重叠时，可以复用当前分支和工作树；出现并发、保护分支或范围风险时必须使用独立分支和 worktree。`composite/epic` 的顶层字段表示集成分支和集成 worktree，协调者必须在进入 `orchestrating` 前创建；切片使用各自 `subflows[].git` 或子 Loop 交付提交。

顶层 `verification_control` 只用于 standard Loop；composite 不使用共享计数器，只读取各 `subflows[].verification_failure_roundtrips` 和 `integration_verification.verification_failure_roundtrips`。首次交验不计入失败往返。

规范文件字段与 required output 映射：

| `files` 字段 | 默认文件 | `required_outputs` ID | 触发条件 |
|---|---|---|---|
| `development_assurance` | `development-assurance.yaml` | `development-assurance` | 新版非 trivial Loop |
| `prototype_behavior_inventory` | `prototype-behavior-inventory.yaml` | `prototype-behavior-inventory` | `product-prototype` |
| `prototype_matrix` | `prototype-implementation-matrix.yaml` | `prototype-implementation-matrix` | `product-prototype` |
| `user_flow_slices` | `user-flow-slices.yaml` | `user-flow-slices` | `product-prototype` |
| `api_contract` | 项目内一个或多个 OpenAPI 文件 | `api-contract` | 原型或数据路线存在服务端承载 |

`files` 使用 snake_case 字段，`required_outputs` 使用 kebab-case 稳定 ID，磁盘文件使用 kebab-case。三者只能按本表转换，不按字符串猜测。

## 审批摘要计算

`artifact_digest` 使用 `sha256-manifest-v1`：

1. `subject_files` 必须包含当前 `requirement.md` 或 `work.md`，以及该需求记录引用的、当前版本全部 `active` 必需需求原型；不包含运行状态和时间戳。
2. 路径使用相对 `project_root` 的 POSIX 形式，按路径字节升序排列。
3. 每个文件对 Git 中待确认版本的原始字节计算 SHA-256，使用小写十六进制。
4. 每项拼成 UTF-8 字节 `path + NUL + sha256 + LF`，顺序连接后再次计算 SHA-256，结果即 `artifact_digest`。
5. 外部产物必须先取得内容 SHA-256，并以 `external:<稳定URI>` 作为 path。

任何 `subject_files` 路径或内容变化都会使原审批失效。`validate` 以及消费该 Gate 的 transition 必须重新计算 manifest，并同时核对 Gate 的 `subject_digest` 与原事件 `artifact_digest`。实现不得自行增删摘要覆盖范围。

当前 Codex 本地插件没有通用的签名 Gate adapter，因此新项目的普通需求、路由和完成 Gate 默认使用 `project.yaml.approval.manual_event_authentication: local_attestation`：记录实际用户消息来源、事件 ID、需求版本和产物摘要，但不宣称密码学证明人类身份。`host_hmac` 保留为显式高强度模式；宿主使用不暴露给执行 Agent 的事件密钥签发 `loop_id + gate_id + decision + actor + source + source_event_id + requirement_version + artifact_digest`，控制程序只导入并验证事件。没有宿主认证能力而策略要求 `host_hmac` 时，Gate 保持 pending，`doctor` 给出 `approval-mode --manual local_attestation` 恢复命令。破坏性操作单独读取 `destructive_event_authentication`，默认仍为 `host_hmac`，不得随普通 Gate 降级。

## 子流程 Schema

`composite` Loop 的 `subflows`：

```yaml
subflows:
  - subflow_id: sf-01-create-refund
    title: 创建退款申请
    required: true
    acceptance_ids: [AC-01, AC-02]
    deliverable: 可创建且不会重复的退款申请
    requirement_version: 1
    state: developing
    state_reason:
    skip_reason:
    main_flow: business-process
    dependencies: []
    scope:
      claim: active
      paths: ["src/refund/**"]
      interfaces: ["POST /refunds"]
      db_objects: ["refunds"]
      states: ["Refund.PENDING"]
    git:
      branch: agentloop/al-20260730-001-sf-01
      worktree: .worktrees/al-20260730-001-sf-01
      last_checkpoint_commit: "<sha>"
    verification:
      policy: flow
      reason: 涉及退款状态和幂等
      reused_flows: [refund-application]
      new_flows: []
      executors:
        refund-application: [code]
    verification_handoff:
      requirement_version: 1
      code_commit: "<sha>"
      affected_existing_flows: [refund-application]
    failure_handoff:
    verification_failure_roundtrips: 0
```

子流程状态只使用：

```text
pending
→ development_preparing
→ developing
→ ready_for_verification
→ verifying
→ passed
```

失败状态为 `failed` 或 `blocked`；无需执行的子流程可标记 `skipped`，但必须填写 `skip_reason`。`required: true` 的单元只有在确认其验收已由其他单元覆盖或需求版本已明确取消时才允许跳过。

## 交付单元合并记录

复合 Loop 的切片分支只合并到 Loop 的集成分支，不直接合并到 `target_branch`。同仓库 epic 也使用同一结构，把各子 Loop 的已验证交付提交合并到父 Loop 集成分支。`git.integration` 记录：

```yaml
git:
  integration:
    status: merging
    base_commit: "<sha>"
    head_commit: "<sha>"
    merges:
      - source_type: subflow            # subflow | child_loop
        source_id: sf-01-create-refund
        source_branch: agentloop/al-20260730-001-sf-01
        source_commit: "<validated-sha>"
        status: merged              # queued | merged | conflict | superseded
        attempts: 1
        max_attempts: 3
        merge_commit: "<sha>"
        merged_by: loop-coordinator
        merged_at: "2026-07-30T15:30:00+08:00"
    post_merge_checks:
      - source_type: subflow
        source_id: sf-01-create-refund
        code_commit: "<integration-head-sha>"
        result: passed
        evidence_id: al-20260730-001-evidence-05
    delivery_commit:
```

`source_commit` 必须等于该切片或子 Loop 通过验证的交付提交。合并、冲突处理、合并后复验和最终交付规则遵守 Git 规则。同仓库 composite/epic 的集成验证只能使用 `git.integration.head_commit`，并将同一值写入 `integration_verification.handoff.code_commit`。

跨仓库 epic 不合并 Git 提交，使用 `integration_verification.handoff.child_deliveries` 锁定每个仓库的已验证交付提交和测试环境。

## 跨交付集成验证

子流程或子 Loop 验证只能证明“交付单元自身正确”，不能自动证明组合正确。存在跨交付接口、状态、数据一致性或完整用户旅程时，必须设置：

```yaml
integration_verification:
  required: true
  reason: 退款创建与支付回退共同修改订单状态
  decided_by: loop-coordinator
  decided_at: "2026-07-30T10:00:00+08:00"
  dependencies: [sf-01-create-refund, sf-02-reverse-payment]
  state: pending
  handoff:
    code_commit: "<integration-head-sha>"
    merged_subflows:
      - subflow_id: sf-01-create-refund
        source_commit: "<sha>"
        merge_commit: "<sha>"
    child_deliveries: []
    changed_interfaces: ["POST /refunds"]
    changed_data: ["refunds", "payments"]
    changed_states: ["Refund.PENDING", "Payment.REVERSED"]
    environment_requirements: ["local-integration"]
  failure_handoff:
    affected_subflows: []
    affected_child_loops: []
    evidence: []
  reused_flows: [refund-end-to-end]
  new_flows: []
  executors:
    refund-end-to-end: [code, ui]
  verification_failure_roundtrips: 0
```

是否需要集成验证不是默认值。协调者必须在 `ready_for_development → orchestrating` 的总体拆分中，根据开发路由明确写入 `required: true/false`、理由、决定人和时间。缺少决定不得进入 `orchestrating`。

开发中发现新的跨交付关系时，协调者必须立即把 `false → true` 并补齐路由；从 `true → false` 需要新的路由依据并通过 `routing_confirmation` 人工 Gate，不能为省测试自动降级。

composite 必须填写 `handoff.code_commit` 和 `merged_subflows`。同仓库 epic 必须先把子 Loop 的已验证交付提交合并到父集成分支，并填写 `handoff.code_commit`；跨仓库 epic 可以省略单一 `code_commit`，但必须在 `child_deliveries` 列出每个子 Loop 的仓库、已验证交付提交和环境版本。

依赖交付单元通过、同仓库交付合并到集成分支且合并后检查通过后，状态依次为：

```text
pending
→ ready_for_verification
→ verifying
→ passed
```

集成失败为 `failed` 或 `blocked`，按影响范围退回相关子流程或子 Loop。第一版每个 Loop 只保留一个集成验证点；需要多个独立集成里程碑时，拆成父子 Loop，由各子 Loop 验证局部集成，父 Loop 验证最终集成。

## 父子 Loop

大型建设使用一个 `loop_kind: epic` 的父 Loop 和多个 `delivery` 子 Loop：

```yaml
loop_kind: epic
child_loops:
  - loop_id: al-20260730-002
    required: true
    acceptance_ids: [AC-01]
    deliverable: 账户服务支持退款冻结
    requirement_version: 1
    dependencies: []
    repository_id: example-project
    project_root: .
    loop_file: .agentloop/loops/al-20260730-002/loop.yaml
    loop_uri:
    skip_reason:
    scope:
      paths: ["services/account/**"]
```

子 Loop 必须记录 `parent_loop_id`。父 Loop 保存总体需求、架构边界和依赖；子 Loop 保存被授权的范围、对应需求版本和自身完整证据。

- 同仓库子 Loop 使用相对 `project_root` 的 `loop_file`，`loop_uri` 留空。
- 跨仓库子 Loop 使用宿主可解析的稳定 `loop_uri`，并填写 `repository_id/project_root`；不得用 `..` 越出当前项目。
- 两种定位方式必须且只能填写一种。无法解析时父 Loop 进入 `blocked`。

父 Loop 不复制子 Loop 状态。协调者每轮聚合前通过 `child_loops[].loop_file` 或 `loop_uri` 读取子 Loop；子 `loop.yaml.state` 是唯一正式来源。无法读取或版本不一致时父 Loop 进入 `blocked`，不得使用旧缓存推进。

完全派生自父需求的子 Loop 可以记录：

```yaml
gates:
  requirement_confirmation:
    gate_id: requirement_confirmation
    status: approved
    mode: inherited_from_parent
    event_id:
    subject_digest: "<child-derivation-digest>"
    inheritance:
      parent_loop_id: al-20260730-001
      parent_requirement_version: 1
      parent_approval_event_id: approval-001
      parent_artifact_digest: "<sha256>"
      derivation_digest: "<sha256>"
      scope_subset_check: passed
      acceptance_subset_check: passed
```

`derivation_digest` 使用审批摘要同样的算法，对子 Loop 的需求记录计算，并同时写入 `subject_digest`。父需求版本变化后，继承立即失效。

出现以下任一情况时，应从子流程升级为独立子 Loop：

- 可独立确认、交付或回滚
- 使用不同负责人、仓库、工作树或发布节奏
- 恢复时无法只加载该单元的需求、开发记录和声明范围
- 需要与其他单元独立并行

## 产物有效性

需求版本变化时，用 `artifacts` 明确标记影响，不删除旧记录：

```yaml
artifacts:
  - artifact_id: al-20260730-001-openapi-01
    type: openapi
    path: docs/openapi.yaml
    status: stale                   # active | stale | superseded
    requirement_version: 1
    produced_by: sf-01-create-refund
    git_commit: "<sha>"
    invalidated_by_requirement_version: 2
    invalidation_reason: 请求字段发生变化
    superseded_by:
```

未受影响的产物保持 `active`。新产物替换旧产物时，旧项设为 `superseded` 并填写 `superseded_by`。

## `requirement.md`、`development.md` 与 `work.md`

`requirement.md` 最低内容：

```text
# 需求名称
## 原始需求与事实
## 用户、场景与目标
## 范围、非目标、规则与约束
## 验收标准
## 分类与复杂度
## 需求原型决定与引用
## 未解决问题
## 确认记录
```

这些标题是内容检查项，不是强制空章节。连续内容可以合并，未触发项可以删除；只要目标、范围、验收、档位和确认依据仍可定位。

`development.md` 最低内容：

```text
# 开发记录
## 输入与需求版本
## 主开发流程及依据
## 现有系统调查
## 编码前产物及检查
## 子流程与依赖
## 实现和修改文件
## 开发自检
## 测试交接
```

`trivial` 的 `work.md` 合并两者，只保留：

```text
# 工作记录
## 需求、范围与验收
## 事实、分类与自动确认依据
## 修改位置与不变行为
## 实现、开发自检与验证结论
```

原型、OpenAPI、数据库脚本和代码保存在项目合适目录，Markdown 只记录相对路径、状态和检查结果。

声明原型实现依据时，`loop.yaml.prototype` 保存类型、四维保真策略和逐页需求；`files.prototype_matrix` 指向实现矩阵。老 Loop 缺少 `prototype` 字段时仍可读取，但任何重新进入需求确认的 Loop 都必须明确写入 `implementation_basis: false` 或完整原型声明。严格原型门禁只在声明原型、选择 `product-prototype` 或 flow 包含 `visual` 时触发。

`loop.yaml.integration_data` 声明前后端真实数据链路。老 Loop 缺少该字段时仍可读取，但任何重新进入需求确认或开发准备的 Loop 都必须显式决定。`required: true` 时四类范围字段均不能为空；`required: false` 时范围为空并记录理由。

## 可复用测试流程定义

`.agentloop/flows/<flow_id>.yaml` 最低结构：

```yaml
schema_version: 1
flow_id: refund-application
title: 退款申请
executor: code
status: active                    # active | needs_review | retired

covers:
  paths: ["src/refund/**"]
  interfaces: ["POST /refunds"]
  routes: ["/orders/:id/refund"]
  db_objects: ["refunds"]
  states: ["Refund.PENDING"]
  tags: [refund, idempotency]

preconditions:
  - 存在已支付订单
steps:
  - action: 提交退款申请
    expect: refund.status == PENDING
  - action: 重复提交相同申请
    expect: refund.count == 1
checks: [response, state, database, idempotency]

automation:
  path: tests/flows/refund-application.test.ts

source_requirements:
  - loop_id: al-20260730-001
    requirement_version: 1
```

测试路由按 `interfaces/db_objects/states` 精确匹配，其次按 `paths`，最后按 `tags`。需求变化可能影响定义但尚未确认时，将 `status` 设为 `needs_review`。

## `evidence.yaml`

只保存真实运行证据索引：

```yaml
schema_version: 1
loop_id: al-20260730-001
runs:
  - evidence_id: al-20260730-001-evidence-01
    flow_id: refund-application
    check_id:
    subflow_id: sf-01-create-refund
    requirement_version: 1
    executor: code
    command: ["npm", "test", "--", "refund-application"]
    result: passed
    exit_code: 0
    counts: {passed: 3, failed: 0, skipped: 0}
    validity: active               # active | stale
    code_commit: "<sha>"
    environment: local-test
    started_at: "2026-07-30T16:00:00+08:00"
    ended_at: "2026-07-30T16:00:08+08:00"
    duration_ms: 8000
    stdout_path:
    stderr_path:
    data_lineage:
      sentinel: "agentloop-7f3a"
      database:
        generated_by: factory
        objects: [refunds]
        observed_sentinel: "agentloop-7f3a"
        evidence_paths: [artifacts/db-row.json]
      backend:
        endpoints: ["GET /api/refunds"]
        observed_sentinel: "agentloop-7f3a"
        evidence_paths: [artifacts/api-response.json]
      frontend:
        routes: ["/refunds"]
        observed_sentinel: "agentloop-7f3a"
        evidence_paths: [artifacts/refunds-page.png]
    artifacts:
      - path: .agentloop/loops/al-20260730-001/artifacts/test-report.json
        sha256: "<hash>"
```

回归只追加新的 `runs`，不复制测试流程定义或测试代码。命令必须使用参数数组；原始输出较长时保存为文件并填写 `stdout_path/stderr_path`，不得塞入 YAML。需求变化影响本次证据时，将 `validity` 设为 `stale`。

每条必需 `acceptance_obligations[]` 必须先映射实现路径和唯一的 flow/check 身份，再由当前提交上的 active passed Evidence 携带同一 `acceptance_id`。`verified` 对必需 ID 做集合差，不能以“存在一条通过记录”代替完整覆盖。同一 Evidence 身份重跑会替代旧运行，因此一次运行覆盖多个义务时必须在新记录中列出全部对应 ID。

UI 原型 evidence 的 `coverage` 必须映射 `prototype_path/route/region_id/interaction_id/acceptance_id/automation_step/evidence_paths`；`visual` 必须记录固定 viewport、对比方式、允许差异、通过标准及逐页参考/实现文件。Markdown 报告只能由 `stdout_path` 或 `artifacts` 引用。

启用 `integration_data` 时，选定 flow 必须包含 `data_lineage` check 且 automation 可执行；active passed evidence 必须使用同一唯一 sentinel 覆盖声明的数据库对象、后端接口和前端路由，并为每层提供存在的证据文件。

产品原型业务 evidence 还必须包含 `test_report` 和 `business_function`。报告由控制程序实际执行 automation 后读取，绑定当前 Git commit，断言数大于零且 `skipped_required == 0`；`business_function.interactions` 覆盖所有非豁免 interaction，`journeys` 至少覆盖创建、编辑、保存、刷新、重登、查询、下游消费和审计。

子流程业务 evidence 的 tested commit 取该子流程最近一次进入 `verifying` 的 transition `git_commit`；父级/集成验证使用 `git.integration.delivery_commit`（无值时依次使用 `git.integration.head_commit`、顶层 `git.head_commit`）。其他子流程或旧 integration commit 不得影响当前子流程绑定。

复合父流程执行视觉与业务完成 Gate 时，聚合 `subflow.state: passed` 的 Evidence。聚合项必须同时满足当前需求版本、当前 `git.integration.delivery_commit/head_commit`、`validity: active`、`result: passed`；不得要求把已经可信通过的子流程 UI Evidence 重写成 `subflow_id: null`，也不得跨提交、跨版本或聚合未通过子流程。

`.agentloop/control/<loop_id>.json` 分阶段保存最后合法摘要：需求确认后锁定分类、验收义务、档位、原型与联调决定；进入开发准备后锁定范围和路由；进入编排后锁定集成及子交付控制字段。只能由控制命令更新；摘要不一致时控制程序恢复快照并中止推进。

新 Loop 固定生成 control v2。活动旧 Loop 缺少 control v2、`acceptance_obligations`、`assumptions`、`decision_records`、`knowledge_state`、`quality_metrics`、`failure_memory` 或 `routing.risk_driver` 任一结构时，`validate` 和推进失败，必须执行 `migrate-v2`；命令初始化新增数组和知识状态、清空旧路由判断、回到 `clarifying`、失效旧 Evidence，并要求重新确认分类、档位、验收义务和风险路由。第一次重新路由必须填写主风险；次要风险必须映射到 supporting flow 或验证义务。已终止历史只读保留。

`quality-metric` 创建 `MET-*` 指标，目标只允许 `gte/lte/eq` 数值比较；填写实测值时必须附证据，`status` 由控制程序计算。required 指标未达标时不能进入 `verified/done`。

`failure-memory` 创建 `FAI-*` 记录，只能引用当前 Loop 中真实的 failed Evidence。记录必须关联已有 `ASM-*` 或 `DEC-*`，无法关联时填写 `unlinked_reason`；可选关联 `MET-*`。所有当前需求版本的 failed Evidence 都必须有失败记忆，且预防措施必须由新的 active/passed Evidence 验证后才能完成。

复用可复用测试流程时填写 `flow_id`；`targeted` 一次性直接检查可以省略 `flow_id`，但必须填写当前 Loop 内稳定且唯一的 `check_id`。两者至少存在一个，不得同时为空。

`routing.verification.policy: self_check` 时不强制创建 `evidence.yaml`；实际检查命令、退出结果和可观察结论直接写入 `work.md`，但不能只写 Agent 推测。

## 状态转换与 Git 检查点

每次状态变化追加：

```yaml
transitions:
  - from: developing
    to: ready_for_verification
    subflow_id: sf-01-create-refund
    actor: development-agent
    at: "2026-07-30T15:30:00+08:00"
    requirement_version: 1
    git_commit: "<sha>"
    evidence: [development.md]
    reason: 开发自检通过并完成测试交接
```

必须先保存和检查产物，再创建 Git 检查点，最后更新状态。当前 `HEAD` 是工作区最新提交的权威来源。

## 并发与恢复

- 同一 Loop 同一时刻只允许一个写入者更新控制文件。
- 修改项目文件的并发 Loop 或子流程必须使用独立 Git 分支和 worktree。
- 开始前声明 `scope.paths/interfaces/db_objects/states`；与活动范围冲突时不得并行。
- `loop.yaml` 和 `evidence.yaml` 使用完整写入后的原子替换。
- YAML 无法解析、路径缺失、哈希错误或需求版本错位时不得前进。
- 恢复时先读 `loop.yaml`，再按当前状态和当前子流程加载必要产物，不加载全部历史。

## 完成检查

```text
loop.yaml 可解析并符合本协议
+ 当前状态与产物一致
+ 需求版本与确认事件一致
+ 当前模式要求的 Markdown 文件存在
+ 当前执行结构满足其一：
    standard → 无未完成执行单元
    composite → 子流程为 passed/skipped、产品 UI 覆盖门禁通过且 git.integration.status == verified
    epic → 必需子 Loop 为 done 或有 `skip_reason` 的 skipped；各子 Loop 原型门禁通过；同仓库集成提交或跨仓库交付集合可定位
+ integration_verification 为 not_required 或 passed
+ 当前验证策略要求的自检记录、可复用测试流程和 evidence 可定位
+ active 产物属于当前需求版本
+ Git baseline 和检查点可查询
+ 没有范围冲突和重复事实来源
```
