# AgentLoop 产物与目录协议

## 目的

本协议是 AgentLoop 文件结构和字段的唯一正式定义。其他协议只引用这里的字段，不得另造同义字段。

目标：

- 人和 Agent 能从项目目录恢复任务
- 同一信息只有一个正式来源
- 简单需求保持最小开销
- 复杂需求能够表达子流程、父子 Loop 和产物失效
- 代码、原型、契约、脚本和测试仍放在项目原有位置

## 术语

为避免“flow 文件”混用，统一使用：

| 术语 | 含义 | 正式位置 |
|---|---|---|
| 开发记录 | 编码前产物索引、实现记录和开发自检 | `development.md`；`trivial` 模式下为 `work.md` |
| 子流程 | 可独立开发和验证的逻辑执行单元 | `loop.yaml` 的 `subflows` |
| 辅助开发流程 | 主开发流程按需组合的编码前方法 | `routing.development.supporting_flows` |
| 可复用测试流程定义 | 可跨需求重复运行的步骤、预期和执行器 | `.agentloop/flows/<flow_id>.yaml` |
| 运行证据 | 某次真实测试或命令运行的结果索引 | `evidence.yaml` |

不得再使用“开发 flow 文件”或用 `flow.md` 表示可复用测试流程。

## 项目内标准目录

```text
<project_root>/
├── .agentloop/
│   ├── project.yaml
│   ├── locks/                       # 运行时锁，不提交 Git
│   ├── loops/
│   │   └── <loop_id>/
│   │       ├── loop.yaml
│   │       ├── requirement.md       # standard / composite
│   │       ├── development.md       # standard / composite
│   │       ├── work.md              # 仅 trivial，合并需求与开发记录
│   │       ├── evidence.yaml        # 有运行证据时创建
│   │       └── artifacts/           # 项目没有更合适位置时才创建
│   └── flows/
│       └── <flow_id>.yaml           # 可复用测试流程定义
├── <项目原有代码和测试目录>
└── <项目原有文档、契约和迁移目录>
```

`.agentloop/` 保存控制信息，不替代项目原有目录规范。

## 执行模式和最小文件

`execution_profile` 是入口复杂度和调度方式，不是需求类型：

| 模式 | 适用情况 | 最小 Loop 文件 |
|---|---|---|
| `trivial`（轻量路径） | 单一、小范围、高置信度变化 | `loop.yaml` + `work.md`；独立测试运行时才增加 `evidence.yaml` |
| `standard` | 一个 Loop 内完成的普通需求 | `loop.yaml` + `requirement.md` + `development.md`；有验证时增加 `evidence.yaml` |
| `composite`（多切片路径） | 包含多个独立子流程的需求 | 与 `standard` 相同，并在 `loop.yaml` 维护 `subflows` |

`trivial` 只允许用于同时满足以下条件的需求：

```text
单一可观察变化
+ 修改位置和影响范围明确
+ 不新增或修改接口、表结构、状态机、权限、安全规则、迁移和外部集成
+ 不需要产品原型
+ 有可直接运行的已有检查或低成本验证
```

任一条件不满足，升级为 `standard`。出现多个可独立交付单元时，升级为 `composite` 或父子 Loop。

入口分流分两次完成：

```text
draft
→ 根据原始输入形成 provisional 档位
→ clarifying 按事实、范围和验收重新判断
→ 需求确认 Gate 前将档位设为 confirmed
```

档位未 `confirmed` 时不得进入开发。需求确认后发现低估复杂度但需求本身未变，可以只升级档位；发现范围或验收变化则必须增加需求版本并重新确认。不得在开发中自动降级以绕过检查。

项目首次接入时额外创建一次 `.agentloop/project.yaml`。只有新增了可长期复用的测试流程时，才创建 `.agentloop/flows/<flow_id>.yaml`。

## 单一事实来源

| 信息 | 唯一正式来源 |
|---|---|
| 状态、路由、审批、子流程、产物有效性和交接索引 | `loop.yaml` |
| 已确认需求、分类、验收标准和需求原型引用 | `requirement.md` 或 trivial 的 `work.md` |
| 开发流程选择、编码前产物和开发自检 | `development.md` 或 trivial 的 `work.md` |
| 测试运行、截图、报告和指标索引 | `evidence.yaml` |
| trivial 自检即验收的检查命令和实际结果 | `work.md` |
| 可复用测试步骤和预期 | `.agentloop/flows/<flow_id>.yaml` |
| 代码、单元测试、UI 自动化和脚本 | 项目原有目录 |
| OpenAPI、Schema、DDL 和迁移脚本 | 项目原有约定目录 |

`loop.yaml` 只保存结构化状态和索引，不复制大段正文。

## 标识规则

```text
loop_id     = al-<YYYYMMDD>-<三位序号>
subflow_id  = sf-<两位序号>-<短名称>
flow_id     = 稳定业务含义，如 refund-application
artifact_id = <loop_id>-<类型>-<序号>
```

ID 创建后不得因标题或内容变化而修改。`flow_id` 只使用小写字母、数字和短横线。

## `project.yaml`

项目配置只创建一次。最低结构：

```yaml
schema_version: 1
project_id: example-project
project_root: .

approval:
  requirement_confirmation:
    mode: manual
    allowed_profiles: []
    minimum_confidence: high
    forbidden_tags: [security-compliance, data-change, external-integration, compatibility]
  routing_confirmation:
    mode: manual_on_low_confidence
  completion:
    mode: human_acceptance
  destructive_actions:
    mode: always_manual

verification_policy:
  defaults:
    trivial: self_check
    standard: targeted
    composite: flow
  self_check_allowed_profiles: [trivial]
  self_check_forbidden_tags:
    [workflow-state, data-change, external-integration, security-compliance, compatibility]

execution:
  workdir: .
  default_timeout_seconds: 120
  max_verification_cycles: 3
  concurrency: separate_worktree

commands:
  bootstrap: ["npm", "install"]
  build: ["npm", "run", "build"]
  typecheck: ["npm", "run", "typecheck"]
  lint: ["npm", "run", "lint"]
  unit_test: ["npm", "test"]
paths:
  source: []
  tests: []
  protected: [".env", "secrets"]
```

允许的审批模式：

- `requirement_confirmation.mode`: `manual` 或 `auto_high_confidence`
- `routing_confirmation.mode`: `manual` 或 `manual_on_low_confidence`
- `completion.mode`: `human_acceptance` 或 `automatic_after_verified`
- `destructive_actions.mode`: 当前只允许 `always_manual`

没有显式配置时全部使用上述保守默认值。Agent 不得自行放宽项目配置。

命令使用参数数组，避免额外 Shell 解释。项目没有的命令直接省略；Agent 不得为填满配置安装新工具或猜测命令。配置不得保存令牌、密码和其他密钥。

## `loop.yaml`

`loop.yaml` 是机器可读入口。以下结构是其他协议必须使用的规范字段：

```yaml

loop_id: al-20260730-001

  coordination: loop-coordinator

  primary_type: 修改现有行为
```

`trivial` 模式的 `files` 只需：

```yaml
files:
  work: work.md
  evidence: evidence.yaml           # policy != self_check 且产生独立运行证据时才需要
```

`trivial` 升级为 `standard/composite` 时：

```text
从 work.md 拆出 requirement.md 和 development.md
→ 检查确认需求内容未被改写
→ 更新 loop.yaml.files 和 execution_profile
→ 在同一 Git 检查点删除 work.md
```

Git 历史保留旧记录，工作区只保留新的单一事实来源。

路径默认相对于当前 `loop.yaml`；项目文件路径相对于 `project_root`，禁止使用 `..` 跳出项目。

## 子流程 Schema

`composite` Loop 的 `subflows`：

```yaml
subflows:
  - subflow_id: sf-01-create-refund
    title: 创建退款申请
    requirement_version: 1
    state: developing
    main_flow: business-process
    dependencies: []
    scope:
      claim: active
      paths: ["src/refund/**"]
      interfaces: ["POST /refunds"]
      db_objects: ["refunds"]
      states: ["Refund.PENDING"]
    git:
      branch: agentloop/al-20260730-001-sf-01
      worktree: .worktrees/al-20260730-001-sf-01
      last_checkpoint_commit: "<sha>"
    verification:
      policy: flow
      reason: 涉及退款状态和幂等
      reused_flows: [refund-application]
      new_flows: []
      executors:
        refund-application: [code]
    verification_handoff:
      requirement_version: 1
      code_commit: "<sha>"
      affected_existing_flows: [refund-application]
    failure_handoff:
    verification_cycles: 0
```

子流程状态只使用：

```text
pending
→ development_preparing
→ developing
→ ready_for_verification
→ verifying
→ passed
```

失败状态为 `failed` 或 `blocked`；无需执行的子流程可标记 `skipped` 并记录原因。

## 跨切片集成验证

子流程验证证明“切片自身正确”，不能自动证明切片组合正确。存在跨切片接口、状态、数据一致性或完整用户旅程时，必须设置：

```yaml
integration_verification:
  required: true
  reason: 退款创建与支付回退共同修改订单状态
  dependencies: [sf-01-create-refund, sf-02-reverse-payment]
  state: pending
  reused_flows: [refund-end-to-end]
  new_flows: []
  executors:
    refund-end-to-end: [code, ui]
  verification_cycles: 0
```

依赖子流程通过后，状态依次为：

```text
pending
→ ready_for_verification
→ verifying
→ passed
```

集成失败为 `failed` 或 `blocked`，按影响范围退回相关子流程。第一版每个 Loop 只保留一个集成验证点；需要多个独立集成里程碑时，拆成父子 Loop，由各子 Loop 验证局部集成，父 Loop 验证最终集成。

## 父子 Loop

大型建设使用一个 `loop_kind: epic` 的父 Loop 和多个 `delivery` 子 Loop：

```yaml
loop_kind: epic
child_loops:
  - loop_id: al-20260730-002
    requirement_version: 1
    dependencies: []
    state: developing
    scope:
      paths: ["services/account/**"]
```

子 Loop 必须记录 `parent_loop_id`。父 Loop 保存总体需求、架构边界和依赖；子 Loop 保存被授权的范围、对应需求版本和自身完整证据。

`child_loops[].state` 镜像子 Loop 的主状态；只有 `done` 或有原因的 `skipped` 计入父 Loop 完成聚合。

出现以下任一情况时，应从子流程升级为独立子 Loop：

- 可独立确认、交付或回滚
- 使用不同负责人、仓库、工作树或发布节奏
- 内容超过单次上下文，恢复时无法只加载当前单元
- 需要与其他单元独立并行

## 产物有效性

需求版本变化时，用 `artifacts` 明确标记影响，不删除旧记录：

```yaml
artifacts:
  - artifact_id: al-20260730-001-openapi-01
    type: openapi
    path: docs/openapi.yaml
    status: stale                   # active | stale | superseded
    requirement_version: 1
    produced_by: sf-01-create-refund
    git_commit: "<sha>"
    invalidated_by_requirement_version: 2
    invalidation_reason: 请求字段发生变化
    superseded_by:
```

未受影响的产物保持 `active`。新产物替换旧产物时，旧项设为 `superseded` 并填写 `superseded_by`。

## `requirement.md`、`development.md` 与 `work.md`

`requirement.md` 最低内容：

```text
# 需求名称
## 原始需求与事实
## 用户、场景与目标
## 范围、非目标、规则与约束
## 验收标准
## 分类与复杂度
## 需求原型决定与引用
## 未解决问题
## 确认记录
```

这些标题是内容检查项，不是强制空章节。连续内容可以合并，未触发项可以删除；只要目标、范围、验收、档位和确认依据仍可定位。

`development.md` 最低内容：

```text
# 开发记录
## 输入与需求版本
## 主开发流程及依据
## 现有系统调查
## 编码前产物及检查
## 子流程与依赖
## 实现和修改文件
## 开发自检
## 测试交接
```

`trivial` 的 `work.md` 合并两者，只保留：

```text
# 工作记录
## 需求、范围与验收
## 事实、分类与自动确认依据
## 修改位置与不变行为
## 实现、开发自检与验证结论
```

原型、OpenAPI、数据库脚本和代码保存在项目合适目录，Markdown 只记录相对路径、状态和检查结果。

## 可复用测试流程定义

`.agentloop/flows/<flow_id>.yaml` 最低结构：

```yaml
schema_version: 1
flow_id: refund-application
title: 退款申请
executor: code
status: active                    # active | needs_review | retired

covers:
  paths: ["src/refund/**"]
  interfaces: ["POST /refunds"]
  routes: ["/orders/:id/refund"]
  db_objects: ["refunds"]
  states: ["Refund.PENDING"]
  tags: [refund, idempotency]

preconditions:
  - 存在已支付订单
steps:
  - action: 提交退款申请
    expect: refund.status == PENDING
  - action: 重复提交相同申请
    expect: refund.count == 1
checks: [response, state, database, idempotency]

automation:
  path: tests/flows/refund-application.test.ts

source_requirements:
  - loop_id: al-20260730-001
    requirement_version: 1
```

测试路由按 `interfaces/db_objects/states` 精确匹配，其次按 `paths`，最后按 `tags`。需求变化可能影响定义但尚未确认时，将 `status` 设为 `needs_review`。

## `evidence.yaml`

只保存真实运行证据索引：

```yaml
schema_version: 1
loop_id: al-20260730-001
runs:
  - evidence_id: al-20260730-001-evidence-01
    flow_id: refund-application
    subflow_id: sf-01-create-refund
    requirement_version: 1
    executor: code
    command: npm test -- refund-application
    result: passed
    validity: active               # active | stale
    code_commit: "<sha>"
    environment: local-test
    started_at: "2026-07-30T16:00:00+08:00"
    artifacts:
      - path: .agentloop/loops/al-20260730-001/artifacts/test-report.json
        sha256: "<hash>"
```

回归只追加新的 `runs`，不复制测试流程定义或测试代码。需求变化影响本次证据时，将 `validity` 设为 `stale`。

`routing.verification.policy: self_check` 时不强制创建 `evidence.yaml`；实际检查命令、退出结果和可观察结论直接写入 `work.md`，但不能只写 Agent 推测。

## 状态转换与 Git 检查点

每次状态变化追加：

```yaml
transitions:
  - from: developing
    to: ready_for_verification
    subflow_id: sf-01-create-refund
    actor: development-agent
    at: "2026-07-30T15:30:00+08:00"
    requirement_version: 1
    git_commit: "<sha>"
    evidence: [development.md]
    reason: 开发自检通过并完成测试交接
```

必须先保存和检查产物，再创建 Git 检查点，最后更新状态。当前 `HEAD` 是工作区最新提交的权威来源。

## 并发与恢复

- 同一 Loop 同一时刻只允许一个写入者更新控制文件。
- 修改项目文件的并发 Loop 或子流程必须使用独立 Git 分支和 worktree。
- 开始前声明 `scope.paths/interfaces/db_objects/states`；与活动范围冲突时不得并行。
- `loop.yaml` 和 `evidence.yaml` 使用完整写入后的原子替换。
- YAML 无法解析、路径缺失、哈希错误或需求版本错位时不得前进。
- 恢复时先读 `loop.yaml`，再按当前状态和当前子流程加载必要产物，不加载全部历史。

## 完成检查

```text
loop.yaml 可解析并符合本协议
+ 当前状态与产物一致
+ 需求版本与确认事件一致
+ 当前模式要求的 Markdown 文件存在
+ 所有必需子流程为 passed/skipped、子 Loop 为 done/skipped
+ 必需的 integration_verification 已 passed
+ 当前验证策略要求的自检记录、可复用测试流程和 evidence 可定位
+ active 产物属于当前需求版本
+ Git baseline 和检查点可查询
+ 没有范围冲突和重复事实来源
```
