# 技术验证驱动流程

## 何时选择

关键技术方案能否满足需求、指标或环境约束仍缺少真实证据。

## 进入输入

- 需要作出的具体决策
- 已确认约束
- 候选方案或待验证假设

## 验证阶段与产出

| 阶段 | 操作 | 明确产出 | 检查与出口 |
|---|---|---|---|
| 1. 定义决策 | 将问题写成一个需要作出的选择 | `development.md` 中的决策问题和候选项 | 结果能够改变后续选择 |
| 2. 定义假设 | 将候选方案改写成可证伪陈述 | 假设、约束和适用范围 | 假设可以被实验结果否定 |
| 3. 定义阈值 | 确定通过、失败和停止标准 | 指标、环境、负载和数值阈值 | 运行前即可判断何时停止 |
| 4. 设计最小实验 | 只实现回答主要问题所需的路径 | 实验步骤、输入数据、变量和预期输出 | 没有混入与决策无关的生产功能 |
| 5. 实现实验 | 编写最少实验代码或脚本 | 可重复运行的实验代码、脚本和命令 | 环境和输入固定或已记录 |
| 6. 真实运行 | 在代表性环境执行并保留原始结果 | 日志、指标、响应、资源消耗或错误结果 | 结果来自真实运行，不是代码推测 |
| 7. 作出判断 | 将结果与预设阈值比较 | `passed`、`failed` 或 `inconclusive`，以及证据引用 | 结论不超出实验覆盖范围 |
| 8. 路由下一步 | 选择方案、放弃方案或设计下一项最小实验 | 决策、适用边界；产品需求的后续开发流程，或技术研究的测试交接 | 后续动作由当前证据直接支持 |

除实验代码、脚本和工具结果外，其余内容默认保存在 `development.md` 中。

## 执行约束

```text
passed
→ 记录适用边界
→ 产品目标中的技术不确定性：进入对应正式开发流程
→ 技术研究：形成 command 验证交接

failed
→ 放弃当前方案
→ 保存证据，避免重复试验

inconclusive
→ 只增加能够消除当前不确定性的下一项实验
```

实验代码默认不进入生产。只有满足生产质量要求且复用明显更省时，才作为正式实现输入。

## 完成

技术验证流程的目的就是取得技术决策证据，因此最小实验必须真实运行；这不是对产品功能的流程验收。

产品目标中的技术不确定性在选定方案后进入正式开发流程，正式代码仍只做开发自检，再交给测试阶段验证。

主要类型为“技术研究”时，实验脚本、初始结果和决策记录就是开发交付；测试 Agent 使用 `command` 执行器在声明环境复跑关键实验并校验预设阈值。通过后按普通 `verifying → verified → done` 完成，不要求生产代码。
