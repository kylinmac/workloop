# AgentLoop 执行、重试与恢复协议

## 目的

本协议规定 AgentLoop 如何启动、执行、重试、暂停和恢复。进度只能依据项目文件、Git、状态记录和实际证据，不依赖对话记忆。

## 单次循环

```text
加载 project.yaml 和 loop.yaml
→ 从独立基线重算当前验收义务和验证身份
→ 校验 Git、状态、审批和当前产物
→ 获取控制文件写锁
→ 检查项目范围占用
→ 选择当前状态允许的一个可检查步骤
→ 执行并检查实际产物
→ 保存证据和 Git 检查点
→ 更新当前子流程或主状态
→ 释放锁
→ 继续，或在 Gate/停止条件结束
```

一个循环默认完成一个可检查步骤。`trivial` 模式允许连续通过已经满足的状态 Gate，但仍必须保存最终需求、修改、真实检查结果和转换记录，不得事后凭空补写。

## 启动

### 新任务

```text
确定 project_root
→ 检查 Git；未初始化时完成安全预检并通过 repository_bootstrap Gate 后建立 baseline
→ 检查或创建 .agentloop/project.yaml
→ 分配 loop_id
→ 创建 loop.yaml，state: draft
→ 根据原始输入选择 provisional execution_profile
→ 按模式创建最小文件
→ 进入 clarifying
→ 在需求确认 Gate 前重新判断并 confirmed
```

### 继续任务

```text
用户指定 loop_id
→ 加载该 Loop

未指定且只有一个非终态 Loop
→ 继续该 Loop

未指定且存在多个非终态 Loop
→ 根据活动 worktree 和明确范围定位
→ 仍不唯一时请求用户选择
```

终态 `done`、`cancelled` 默认不恢复。项目配置结构、审批策略和规范字段见[产物与目录协议](产物与目录协议.md)。

## 编排执行

`owners.coordination` 是 Loop 的唯一主状态写入者。它每轮选择一个当前可执行单元并交给对应角色；角色完成实际产物后返回交接，协调者再更新主状态和聚合结果。

同一 Agent 可以承担协调、需求、开发或测试角色，但必须逐次切换并记录当前 `actor`。多 Agent 模式下，子流程负责人不得越过协调者直接修改父状态；协调者也不得代替需求负责人审批或代替测试 Agent 声明测试通过。

`self_check` 路径没有测试角色的通过声明：开发 Agent 记录真实检查结果，协调者只按既定策略推进状态。

## Git 与入口门禁

任何项目修改前必须：

- 项目由有效 Git 仓库管理；否则先初始化并建立初始提交。
- `baseline_commit` 可查询。
- 用户已有修改已识别且不会被覆盖。
- 当前 Loop 或子流程的修改范围已声明。

具体遵守[Git 版本控制与可追溯规则](../rules/Git版本控制与可追溯规则.md)。

无其他活动 Loop、范围不冲突、目标分支不受保护且用户已有修改不重叠时，trivial/standard 可以复用当前分支和工作树。并发、复合或 epic 必须使用独立分支和 worktree。

## 锁与并发

### 控制文件锁

同一 `loop_id` 同时只允许一个写入者更新控制文件：

```text
.agentloop/locks/<loop_id>.lock
```

```yaml
execution_id:
actor:
started_at:
heartbeat_at:
lease_until:
```

锁目录加入 `.gitignore`。租约过期后仍须检查 Git、状态和进程事实，不能只按时间删除。

### 项目修改范围

单 Loop 写锁不能防止多个 Loop 修改同一文件。任何并发修改还必须满足：

```text
各自使用独立 Git 分支和 worktree
+ scope.paths/interfaces/db_objects/states 已声明
+ 活动范围没有冲突
+ 不共享可变测试环境
+ 不依赖对方未完成产物
+ 可以分别提交和回滚
```

检测到路径、接口、数据库对象或状态范围冲突时：

```text
能够建立明确依赖
→ 顺序执行

不能安全排序
→ blocked
→ 由负责人重新划分范围
```

范围比较采用保守规则：接口、数据库对象和状态按规范化名称精确比较；路径先解析到当前仓库内的实际已存在文件，并比较计划新增路径。两个 glob 无法证明互斥时视为冲突，不得仅因字符串不同判定可并行。

composite、epic 和并发修改默认一个执行单元对应一个 worktree；无并发的 trivial/standard 可以复用当前工作树，不为隔离形式增加不必要的合并复杂度。

范围登记必须在持有 `.agentloop/locks/project-scope.lock` 时完成：

```text
取得项目范围锁
→ 扫描全部非终态 Loop 和子流程的 active scope
→ 无冲突时把当前 scope.claim 写为 active
→ 保存 loop.yaml
→ 释放项目范围锁
```

完成、取消或安全清理工作树后，将 claim 改为 `released`。`blocked` 且仍有未合并修改时继续占用范围。这样两个 Loop 不能同时通过同一次无冲突检查。

## 执行单元

每个步骤必须声明：

```yaml
step_id:
state:
subflow_id:
operation:
inputs:
expected_outputs:
check:
idempotency:
```

执行前检查输入，执行后检查真实产物。没有可检查产物或状态变化的操作不能完成。

当前执行记录写入 `loop.yaml.execution`，字段以产物协议为准。`targeted/flow` 的命令、退出状态、堆栈和输出索引写入 `evidence.yaml`；`self_check` 的命令、实际结果和结论写入 `work.md`。

## 审批 Gate

审批策略来自 `project.yaml.approval`。

### 人工确认

只接受宿主系统记录并绑定当前 Loop、Gate、需求版本和产物摘要的事件。Agent 可以读取和引用事件，不能自行填写人工 `actor`、时间或来源 ID。当前状态写入 `loop.yaml.gates`，历史追加到 `gate_events`。

对话中的确认只有被宿主转换为规范审批事件后才有效。

### 自动确认

仅当策略明确允许且状态机的全部资格条件满足时通过。每次自动通过仍须记录：

```yaml
gate_id:
decision: approved
actor: agent-policy
mode: auto_high_confidence
confidence:
policy_snapshot:
requirement_version:
artifact_digest:
at:
```

自动事件也必须由宿主分配 `event_id/source_event_id`。自动确认条件任一不满足即转人工，不得降低置信度阈值。破坏性操作永远人工确认。

## 幂等与重复执行

```text
产物存在且检查通过
→ 不重复执行
→ 补齐状态记录

产物不存在
→ 可以重新执行

产物存在但不完整
→ 根据 Git diff 和证据恢复或修正
→ 不盲目覆盖
```

迁移、批处理和外部写入必须先明确重复运行结果、幂等键、继续位置、停止条件和回滚或补偿。无法说明后果时禁止自动重试。

同一 `loop_id + requirement_version + scope + flow/check` 开始新测试运行时，旧的 active Evidence 立即变为 `superseded`。新运行失败、中断或断言为零时仍保持替代关系，禁止回退使用旧 passed 结果。

## 失败分类和步骤重试

| 分类 | 处理 |
|---|---|
| 瞬时失败 | 输入不变时可在剩余次数内重试 |
| 确定性执行失败 | 先修改代码、测试、配置或输入，再尝试 |
| 需求错误 | 退回 `clarifying` |
| 开发路由错误 | 退回 `development_preparing` |
| 权限、人工决策或破坏性操作 | 停止并等待有效审批 |
| 状态、产物或 Git 损坏 | 停止并执行恢复 |

同一执行单元默认最多三次，第一次计入。相同失败指纹连续三次或次数耗尽时进入 `blocked`。

失败指纹由：

```text
step_id
+ subflow_id
+ 失败分类
+ 命令或断言
+ 主要错误信息
```

安全拒绝、权限不足、需求不明确和不可逆操作不自动重试。

## 开发与测试往返熔断

步骤 `max_attempts` 不能代替整个开发—测试循环上限。

首次从 `developing → ready_for_verification` 不计数。只有测试已经开始，并因实现错误发生：

```text
verifying
→ developing
→ 修复后再次 ready_for_verification
```

才算一次失败往返：

```text
standard
→ verification_control.failure_roundtrips += 1

composite 切片
→ 当前 subflows[].verification_failure_roundtrips += 1
→ 不增加父级计数器，也不影响其他切片

integration_verification 失败并修复后重交
→ integration_verification.verification_failure_roundtrips += 1
```

`verification_control` 只用于 standard Loop；composite 使用各切片和集成验证自己的计数器。上限来自 `project.yaml.execution.max_verification_failure_roundtrips`，未配置时为 3。

```text
failure_roundtrips < max_failure_roundtrips
→ 按失败影响范围修复并重测

failure_roundtrips >= max_failure_roundtrips 且仍未通过
→ blocked
→ 保存历次失败指纹、修改提交和未收敛原因
→ 请求人工决定继续、改需求、换路线或取消
```

修改项目上限必须有负责人授权，Agent 不得自行清零计数。

## 测试失败循环

```text
verifying 发现实现错误
→ 保存 failure_handoff 和原始证据
→ 当前普通 Loop 或子流程回到 developing
→ 修复并完成开发自检
→ 新 Git 提交
→ 增加当前执行单元的 failure_roundtrips
→ ready_for_verification
→ 重跑原失败流程、受影响分支和必须保持不变的相邻流程
```

测试 Agent 不直接修改生产代码。需求错误退回 `clarifying` 并增加需求版本。

## 控制协议五路径回归

修改 Schema、状态转换、Gate、Evidence 或恢复逻辑时，必须在同一变更中验证：

```text
合法输入正常推进
+ 缺项、伪造或身份不符时关闭门禁
+ 修复后重跑替代旧 Evidence
+ completion 拒绝后只退回受影响范围
+ 旧版本产物经明确迁移或豁免后可恢复
```

只测试首次正常通过不能证明控制协议可用。

## 需求变化和产物失效

需求版本增加后必须按影响范围逐项处理：

```text
设计、代码、契约或脚本受影响
→ artifacts[].status: stale

旧产物已被新产物替换
→ status: superseded
→ 记录 superseded_by

运行证据基于失效预期或代码
→ evidence.runs[].validity: stale

可复用测试流程可能受影响
→ 对应 `.agentloop/flows/<flow_id>.yaml` 的 status: needs_review

确认无影响
→ 保持 active
```

Git 检查点、产物和证据必须记录对应 `requirement_version`。不得无差别删除或全部复用。

旧版本产物恢复时，可以读取旧字段来定位范围和生成迁移输入，但不得把它们直接当成新 Gate 已通过。恢复命令先写入迁移决定和最小补充项，再退回相应准备状态；只有状态已合法退回后才执行新版严格入口检查，避免“必须先满足新门禁才能进入补齐新门禁产物的状态”这一循环锁死。

completion Gate 发现原型不一致时，以实现矩阵中的 `prototype_path/route/subflow_id` 为恢复索引。只失效覆盖受影响页面的 UI evidence；旧 evidence 没有逐页 coverage 时视为无法证明不受影响并标记 stale。普通 Loop 回到 `development_preparing`，复合/epic 只把相关产品 UI 子流程退回 `development_preparing`，父 Loop 保持 `orchestrating`。`failure_handoff` 必须保留失败原因、受影响页面/路由、stale evidence ID 和重验范围。

## 子流程调度

依赖全部 `passed/skipped` 后，子流程才能从 `pending` 进入 `development_preparing`。

每个子流程独立保存：

- 当前状态
- 修改范围和依赖
- Git 分支、worktree 和检查点
- 测试交接
- 验证失败往返次数

主状态使用状态机的聚合规则。不同子流程可以处于 `developing` 和 `verifying`，但共享范围或环境时必须顺序执行。

切片 `passed` 后不直接进入集成验证：

```text
记录通过验证的 source_commit
→ 协调者按 Git 规则合并到 Loop 集成分支
→ 冲突则退回责任切片 developing
→ 全部合并后在 integration head 上重跑切片定向检查
→ 失败则退回受影响切片
```

只有全部依赖切片已合并且合并后检查通过，才处理：

```text
integration_verification.required == false
→ state: not_required

integration_verification.required == true
→ handoff.code_commit = git.integration.head_commit
→ 进入 ready_for_verification
→ 执行跨切片验证
→ passed 后才允许父状态 verified
```

集成失败时只退回证据指向的子流程；无法定位责任切片时进入 `blocked`，由协调者重新拆分问题。

epic 聚合前，协调者必须通过 `child_loops[].loop_file` 或 `loop_uri` 逐个读取子 Loop，校验 `parent_loop_id` 和需求版本，并使用子 `loop.yaml.state` 计算结果。父 Loop 不保存或信任子状态副本；对子 Loop 为 `done` 的结果还必须重新检查其原型矩阵、visual evidence、automation 和验收到证据映射。子文件缺失、解析失败、版本不一致或语义门禁失败时父 Loop 不得推进。

同仓库 epic 在子 Loop 完成后，把各自的已验证交付提交按依赖顺序合并到父集成分支，执行各子交付的 `targeted/flow` 检查，再按 `integration_verification.required` 决定是否执行跨交付验证。跨仓库 epic 不合并提交，只锁定 `child_deliveries` 后执行能够覆盖多仓库环境的集成验证。

## 中断恢复

控制快照缺失不是“首次运行”。所有正常 init 都会创建快照，因此缺失时 `status/validate/transition/evidence` 必须失败。恢复只能执行：

```text
agentloop repair-control <loop_id> --from-commit <可信提交>
→ 校验 Git 中快照自身摘要
→ 恢复快照
→ 按快照恢复受控字段
→ 再次 validate
```

不得按当前 `loop.yaml` 静默重建。Evidence 的 result、commit、flow/check、scope、requirement version 和 validity 都属于受控摘要。

项目内 `.agentloop/schemas` 与插件版本不一致时运行 `agentloop runtime-upgrade`，原子覆盖 Schema 和示例参考副本；实际 Loop 数据仍按明确兼容/迁移规则处理，不由升级命令猜测改写。

```text
解析 project.yaml 和 loop.yaml
→ 检查 Git baseline、branch、worktree、HEAD 和工作区
→ 检查 execution、当前 subflow 和最后 transition
→ 检查审批事件、预期产物和 evidence
→ 判断最后步骤是否实际完成
→ 补状态、继续、退回或 blocked
```

### 操作完成但状态未更新

产物存在、检查通过且提交可定位：不重复执行，补 evidence 和 transition。

### 存在未提交修改

查看 diff，确认归属并运行当前检查。通过则建立检查点；无法判断归属或混入用户修改时进入 `blocked`。禁止使用 `git reset --hard` 或覆盖目录恢复。

### 状态前进但产物缺失

从 Git 恢复最后有效的状态文件，记录恢复转换，回到缺失产物所属状态。

### 提交存在但元数据缺失

通过包含 `loop_id/subflow_id/requirement_version` 的提交信息和实际 diff 确认归属后补写索引。

## 必须停止

- 人工审批 Gate 尚未通过
- 路由置信度为 `low`
- 需要权限或破坏性操作批准
- 范围冲突无法安全排序
- 敏感文件可能被提交
- 状态、产物或 Git 基线不可信
- 验收义务集合或 Evidence 验证身份无法唯一确定
- 验证失败往返达到上限
- `blocked`、`done` 或 `cancelled`

停止时记录当前状态、当前子流程、已有产物、原因和解除条件。

## 完成

```text
当前执行结构满足其一：
    standard → 无未完成执行单元
    composite → 必需子流程 passed/skipped 且 git.integration.status == verified
    epic → 必需子 Loop done 或有依据的 skipped；同仓库父集成提交已验证，或跨仓库交付提交集合可定位
+ integration_verification 为 not_required/passed
+ state == verified
+ completion Gate 已通过
+ 从独立基线重算的必验集合覆盖完整
+ 当前验证策略要求的 work.md 自检或精确身份 active Evidence 可定位
+ Git 检查点可查询
+ 没有未处理阻塞
→ done
```

`done` 不代表已经发布到生产。
