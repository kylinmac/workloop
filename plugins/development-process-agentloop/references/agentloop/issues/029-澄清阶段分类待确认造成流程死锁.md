# 澄清阶段分类待确认造成流程死锁

## 现象
新建 composite Loop 保持 `draft + primary_type: 待确认`，仓库级 `validate` 却报分类未确认。
## 影响
新 Loop 无法合法进入需求澄清，只能停滞或诱使调用方绕过控制文件。
## 根因
校验器本已放行新 Loop 的 `draft/clarifying`，但会校验同仓库所有 Loop；一个在澄清前取消、仍保留待确认分类的旧 Loop 被当成确认后状态，错误污染了全局结果。
## 旧门禁为何没拦截
回归只覆盖了活动 composite 初始化，没有覆盖“未确认即取消的旧 Loop + 新 Loop”组合。
## 修复
`draft/clarifying`、澄清前 blocked 和 cancelled 均允许分类待确认；`clarifying → awaiting_requirement_confirmation` 继续强制分类完整。
## 回归
先取消未确认 composite，再新建 composite；验证其 draft/clarifying 可通过，而进入需求确认 Gate 仍失败。
## 预防规则
仓库级聚合校验必须区分活动阶段义务和终止时保留的历史事实，终态旧 Loop 不得污染新 Loop。
