# 单体 Skill 与全量 Loop 造成上下文膨胀

## 现象

插件只有一个 359 行 Skill，并要求每轮读取完整 `loop.yaml`。需求、开发、验证、集成、恢复规则以及不断增长的转换和 Gate 历史同时进入模型上下文，少量对话后即触发压缩。

## 影响

无关阶段信息挤占任务上下文，增加检索遗漏和规则冲突概率；Composite Loop 越运行越大，后续阶段承担全部历史成本。

## 根因

插件把“持久控制状态完整”和“模型每轮需要看到完整状态”混为一件事，也把一个插件误实现成一个单体 Skill，没有阶段路由和只读状态投影。

## 旧门禁为何没拦截

既有回归验证状态正确性、Gate 和 Evidence 门禁，但没有上下文字段隔离、Skill 大小或投影体积预算。

## 修复

- 保留完整 `loop.yaml` 作为受保护底账，新增 `context` 命令按状态生成只读投影并携带源摘要。
- 将单体 Skill 拆为薄路由及需求、开发、验证、集成、完成、恢复六个阶段 Skill。
- Composite 父级只显示子流程摘要，单元工作使用 `--subflow-id` 独立投影。
- SessionStart Hook 改为引导读取阶段投影，完整底账只用于恢复和控制诊断。

## 回归

- 校验需求、开发和完成投影不包含各自无关字段。
- 校验需求投影小于完整 Loop 的 70%。
- 校验路由 Skill 不超过 80 行、阶段 Skill 不超过 60 行。
- 完整 AgentLoop 生命周期回归继续通过。

## 预防规则

新增状态字段首先进入控制底账；只有当前阶段作决策必需的字段才能进入阶段投影。任何新增全局提示都必须证明无法由控制程序或阶段 Skill 承担。
