# 需求分类

## 职责

需求分类用于判断“这次需求是什么性质的变化”，不是选择需求确认流程，也不直接决定开发流程。

所有需求共用一个需求确认主流程。分类只负责：

- 触发必须补充的需求核对项
- 标明与现有系统的关系
- 提醒开发阶段重点关注的风险
- 提醒测试阶段哪些行为需要新增验证或回归

## 分类结构

每个需求记录：

```text
一个主要类型
+ 零个或多个特征标签
```

主要类型表示需求的核心变化性质；特征标签表示跨类型的风险和约束。

`trivial / standard / composite` 不属于需求分类，而是 AgentLoop 的执行复杂度模式：分类回答“是什么变化”，执行模式回答“需要多少产物和怎样调度”。两者分别记录，不互相替代。

## 八类主要类型

### 1. 从 0 建设

不存在对应的系统或独立模块，需要建立新的产品或系统能力。

必须补充：

- 目标用户和核心场景
- 产品与系统边界
- 最小可交付范围
- 成功标准
- 可复用的现有能力；如果存在

### 2. 新增能力

在现有系统边界内增加新的业务能力。

必须补充：

- 新能力解决的问题
- 与现有能力的关系
- 新增范围与非目标
- 不能影响的现有行为
- 新能力的验收标准

### 3. 修改现有行为

已经存在的业务规则、处理流程、接口行为或用户交互需要按新预期改变。

必须补充：

- 当前行为及事实依据
- 目标行为
- 当前与目标的差异
- 修改原因
- 必须保持不变的行为
- 兼容要求

### 4. 缺陷修复

已经确认的预期没有变化，但系统实际行为偏离预期。

必须补充：

- 实际问题现象
- 预期行为
- 预期行为的需求、契约或规则依据
- 影响用户和场景
- 严重程度

根因调查和修复方案属于开发阶段。

### 5. 内部改进

外部行为原则上保持不变，主要改善代码结构、性能、安全、稳定性、可维护性或可观测性。

必须补充：

- 当前问题或基线
- 需要改善的指标
- 目标值或完成条件
- 必须保持不变的外部行为
- 允许修改的范围

### 6. 迁移升级

对技术、数据、接口、服务或运行环境进行新旧转换。

必须补充：

- 当前状态和目标状态
- 迁移对象和范围
- 兼容窗口
- 可接受停机
- 数据保留要求
- 停止与回退要求
- 迁移完成标准

### 7. 下线删除

移除功能、接口、字段、依赖、数据或系统。

必须补充：

- 当前使用方和调用方
- 下线或删除范围
- 数据保留要求
- 兼容过渡期
- 恢复要求
- 删除完成标准

### 8. 技术研究

最终交付物是技术结论、可行性证据或方案选择，而不是直接交付产品功能。

必须补充：

- 需要作出的决策
- 已知约束
- 候选方向
- 成功、失败和停止标准
- 结论将影响的后续工作

如果最终目标仍是产品功能，只是存在技术不确定性，应使用其他主要类型并增加 `technical-uncertainty` 标签。

## 特征标签

### `ui-interaction`

涉及页面、交互或用户路径。

补充核对：目标用户、核心操作、页面结果，以及是否需要需求原型。

### `workflow-state`

涉及多角色、多步骤、状态变化、异常或补偿。

补充核对：角色、主流程、关键分支、失败结果和业务终点。

### `data-change`

涉及数据、数据结构、数据口径、导入导出、修复或回填。

补充核对：数据范围、数据量、正确性标准、备份恢复和处理后核对方式。

### `external-integration`

涉及第三方服务或其他内部系统。

补充核对：责任边界、认证权限、数据安全、可用性要求和外部不可用时的业务结果。

### `security-compliance`

涉及敏感数据、权限、审计、法规或合规要求。

补充核对：数据级别、角色权限、禁止行为、审计要求和合规依据。

### `performance-capacity`

涉及响应时间、吞吐、并发、资源或容量。

补充核对：负载条件、当前基线、目标阈值和测量环境。

### `compatibility`

需要保持旧客户端、旧接口、旧数据或旧流程可用。

补充核对：兼容对象、兼容范围、兼容期限和退出条件。

### `technical-uncertainty`

产品目标明确，但关键技术能否实现仍缺少证据。

补充核对：技术约束和产品验收标准；具体实验问题由开发阶段的技术验证流程确定。

## 判断顺序

```text
交付物主要是技术结论
→ 技术研究

不存在对应系统或模块
→ 从 0 建设

移除已有能力
→ 下线删除

进行新旧转换
→ 迁移升级

预期不变但实际错误
→ 缺陷修复

外部行为不变并改善内部质量
→ 内部改进

改变已有预期行为
→ 修改现有行为

增加新的业务能力
→ 新增能力
```

无法确定主要类型，说明目标、范围或当前事实仍不明确，应返回需求澄清。

## 分类结果

分类结果直接记录在需求文件中：

```text
主要类型：
特征标签：
分类依据：
由类型触发的补充核对项：
由标签触发的补充核对项：
主要验收与回归重点：
```

不为分类结果单独创建文档。

### 机器闭环

新版 Loop 的 `classification.control_version: 2` 必须把分类结果写入 `loop.yaml`：

- `basis`：为什么选择该主要类型，以及同时命中其他类型时的排除依据。
- `obligations[]`：逐项记录 `obligation_id/kind/requirement/source/status`。
- `kind` 必须覆盖本类型“必须补充”的全部项目；控制程序按主要类型做集合差检查。

`source` 必须指向独立需求、契约、现状证据或用户确认记录，不能写“Agent 已检查”。主要类型仍为“待确认”、义务缺项、ID 重复或来源为空时，不得进入需求确认 Gate。旧 Loop 继续按 v1 读取；重新确认时通过 runtime upgrade 迁移到 v2。

同时命中多个类型时只保留一个主要类型，但 `basis` 必须说明核心交付物、其他命中项为何降为标签或 supporting flow。判断顺序是默认优先级，不是跳过冲突说明的依据。

## 与开发流程的关系

需求分类是开发流程选择的输入，但不与开发流程一一对应。

```text
主要类型：新增能力
特征标签：ui-interaction、external-integration

开发阶段仍可能根据主要不确定性选择：
├── 产品原型驱动流程
├── 数据与契约驱动流程
├── 业务流程驱动流程
└── 快速变更流程
```

缺陷修复、迁移升级和技术研究有明显的推荐开发流程，但仍由开发总览根据实际情况确认。
