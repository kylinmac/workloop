# 测试验证流程体系总览

## 总览职责

本总览先决定验证开销；只有策略为 `targeted/flow` 时，测试 Agent 才接收 `ready_for_verification`：

```text
是否允许 self_check，还是必须 targeted / flow
→ 当前需求要验证什么
→ 拆成哪些可独立验证的验证单元
→ 每个验证单元使用哪个执行器
→ 需要增加哪些检查标签
→ 进入对应的详细流程执行
```

产物约束、通过条件和失败处理遵循[测试验证流程定义规则](测试验证流程定义规则.md)，本总览不重复定义。

进入输入包括执行档位、风险标签、已确认需求和验收标准、实现代码、开发自检结果、影响范围以及测试交接信息。

复合 Loop 每次只接收一个 `ready_for_verification` 子流程，结果写回该子流程；其他子流程可以继续开发。全部依赖切片通过后，按需执行 `integration_verification`，父状态在切片和集成验证全部通过前保持 `orchestrating`。

## Agent 选择流程

```text
读取需求、验收标准和开发产物
→ 选择验证策略
    ├── trivial、单一确定结果、无禁止风险且结果可直接观察
    │   → self_check
    │   → 开发阶段直接检查，不进入本阶段
    ├── 已有测试或定向命令可以可靠覆盖
    │   → targeted
    └── 新业务路径、跨模块或高风险行为
        → flow
→ targeted / flow 根据 covers 索引查找已有流程定义和测试
    ├── 已有流程能够覆盖
    │   → 直接复用
    │   → 确认预期保持不变还是按需求改变
    └── 没有流程能够覆盖
        → 仅 policy == flow 且存在新增独立路径时，才新增可复用测试流程
→ 判断每个验证单元需要什么方式取得可信结果
    ├── 代码、接口、数据或状态可直接断言
    │   → 代码流程验证
    ├── 必须经过真实页面操作并检查用户可见结果
    │   → UI 流程验证
    └── 必须运行命令、迁移、负载、故障或实验程序
        → 命令与实验流程验证
→ 增加必要的检查标签
→ 执行对应详细流程
```

回归验证不单独建立流程。它只是重新执行已有流程：

```text
预期未改变
→ 原测试和断言原样重跑

预期明确改变
→ 只更新原流程中受影响的预期和断言
→ 未声明改变的结果仍必须保持一致
```

检索顺序为接口、数据库对象和业务状态精确匹配，路径匹配，其次标签匹配。多个候选无法确定时不得猜测，按低置信度路由处理。

## 执行器入口

- [代码流程验证](flows/代码流程验证.md)
- [UI 流程验证](flows/UI流程验证.md)
- [命令与实验流程验证](flows/命令与实验流程验证.md)

一个验证单元默认只选择一个主执行器。只有单个执行器无法覆盖验收结果时才组合，例如：

```text
下单流程
→ UI 执行器验证用户点击和页面结果
→ 代码执行器验证订单、库存和支付状态
```

## 分类标签

执行器确定“怎么运行”，标签确定“额外检查什么”：

```text
response
state
database
event
permission
idempotency
compatibility
migration
performance
security
visual
interaction
```

标签只决定增加什么断言和证据，不再产生独立流程文档。

## `targeted/flow` 执行闭环

```text
流程定义
→ 可执行测试或脚本
→ 真实运行
→ Assert 或等价判定
→ 保存工具生成的运行证据
→ 通过，或修复后重跑
```
