# 测试验证流程定义规则

## 阶段边界

测试验证阶段在开发状态达到 `ready_for_verification` 后开始。

进入输入至少包括：

- 已确认需求和验收标准
- 待验证代码和版本
- 开发自检及单元测试结果
- 实现范围和影响范围
- 测试交接信息

开发阶段的编译、静态检查和单元测试用于保证代码基本正确，不能代替本规则要求的业务流程、用户流程、数据流程或实验流程验证。

## 测试单元

测试以一个有业务意义、能够独立跑通并判断结果的流程为单元。

```text
一个测试类或测试文件
→ 对应一个业务流程、用户流程、数据流程或实验流程

一个测试方法或场景
→ 对应正常路径、关键分支或失败路径
```

不以简单函数为主要验收单元，也不把整个系统全部功能塞进一个测试。

## 唯一核心闭环

```text
确定需要验证的业务流程
→ 查找已有流程定义和测试
→ 优先复用；缺失时才新增
→ 确认本次预期保持不变还是按需求改变
→ 真实运行
→ Assert 验证
→ 保存证据
→ 通过，或修复后重跑
```

## 三类必备产物

每个被验证的流程都必须能找到以下三类产物。新流程需要创建，回归流程直接复用已有流程定义和测试，只新增本次运行证据。

### 流程定义

一个 `.agentloop/flows/<flow_id>.yaml`，至少包含：

- 流程目标
- `covers.paths/interfaces/routes/db_objects/states/tags` 覆盖索引
- 前置条件
- 测试账号和数据
- 连续执行步骤
- 每一步预期结果
- 中间检查点
- 最终结果
- 关键失败路径
- 使用的执行器

### 可执行测试

必须是项目能够直接运行的测试类、测试文件或脚本。

测试必须：

- 准备或明确前置状态
- 按流程顺序执行
- 对关键检查点 Assert
- 对最终业务结果 Assert
- 失败时输出可定位信息
- 可以安全重复运行

### 运行证据

必须来自真实执行，至少包含：

- 测试命令
- 代码和测试版本
- 环境
- 通过、失败和跳过数量
- 失败断言和堆栈
- 测试框架原始报告
- 日志、请求响应、数据结果或截图；按执行器产生

AI 阅读代码后推测“应该通过”不算运行证据。

## 最小文件规则

默认只保留：

```text
一个可复用测试流程 YAML
+ 一个测试类、测试文件或脚本
+ 工具自动生成的运行结果
```

这是新建流程时的最小产物。已有流程进行回归时，直接复用原测试流程定义和测试，只新增本次工具运行结果。

流程范围、环境、步骤、预期和状态合并在同一个 YAML 中。字段结构遵守[AgentLoop 产物与目录协议](../agentloop/产物与目录协议.md)。

成功时不再额外生成测试计划、执行记录、回归总结和最终报告等重复文档。失败时才增加问题记录和重跑证据。

测试分类只用于选择执行器和检查标签，不为每个标签建立独立流程。

## 回归复用规则

回归不是新的测试流程分类，也不新增执行器。

```text
已有流程，本次行为应保持不变
→ 直接运行原测试
→ 原步骤、断言和结果必须保持一致

已有流程，本次需求明确改变预期
→ 在原流程中更新受影响的预期和断言
→ 运行修改后的流程
→ 同时确认未声明改变的步骤和结果保持一致

本次新增了原流程无法表达的独立业务路径
→ 才新增可复用测试流程定义和可执行测试
```

回归范围根据开发交付的影响范围选择：

- 本次直接修改的流程
- 共用同一代码、接口、数据或状态的流程
- 必须保持不变的相邻流程
- 缺陷修复对应的原失败流程

回归默认产出只有新的运行证据。不要复制一份“回归流程文档”或“回归测试类”。

## 流程检索规则

测试 Agent 不按名称猜测已有流程，必须使用 `covers` 索引：

```text
接口、数据库对象、业务状态精确匹配
→ 优先

修改路径匹配
→ 其次

标签匹配
→ 最后补充
```

匹配到多个候选且无法确定时，路由置信度为 `low`，先确认影响范围。需求变化可能使已有流程失效时，将其标记为 `needs_review`，核对后再运行。

## 三种执行器

### 代码测试执行器

用于后端、接口、领域、数据、迁移和代码级端到端流程。

典型产物：测试类、测试脚本、Assert 结果、测试框架报告。

### UI 测试执行器

用于页面和用户点击流程。

典型产物：浏览器自动化文件、页面断言、步骤截图、失败录像。

### 命令与实验执行器

用于性能、安全、迁移命令、故障恢复和技术实验。

典型产物：可重复命令或脚本、原始指标、阈值断言和运行报告。

## 验证标签

接口、状态、权限、幂等、数据、安全等不是独立流程，而是流程的检查标签。

```yaml
checks:
  - response
  - state
  - database
  - permission
  - idempotency
```

标签决定流程中增加哪些断言，不产生一套新的流程。

## 失败与回归

失败后保存原始证据，判断是需求、设计、实现、环境、数据还是测试代码问题。

修复后至少重跑：

- 原失败场景
- 同一流程正常路径
- 受影响分支
- 必须保持不变的相邻流程

只有失败时才创建问题记录；成功流程不额外生成总结文档，测试报告和流程状态就是结论。

## 完成条件

```text
流程定义存在
+ 可执行测试存在
+ 测试真实运行
+ 关键结果有 Assert
+ 运行证据已保存
+ 状态明确为 passed 或 failed
```
