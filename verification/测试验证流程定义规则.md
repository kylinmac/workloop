# 测试验证流程定义规则

## 阶段边界

独立测试验证阶段只在普通 Loop 的 `routing.verification.policy` 或复合切片的 `subflows[].verification.policy` 为 `targeted/flow`，且对应状态达到 `ready_for_verification` 后开始。

进入输入至少包括：

- 已确认需求和验收标准
- 待验证代码和版本
- 开发自检及单元测试结果
- 实现范围和影响范围
- 测试交接信息

## 验证策略

```text
self_check
→ 仅限 trivial、单一确定结果和低风险标签
→ 开发 Agent 直接运行最小检查
→ 结果写入 work.md
→ 不创建测试流程定义、测试文件或 evidence.yaml

targeted
→ 运行已有测试流程、已有测试或直接检查命令
→ 只覆盖本次修改、受影响分支和必须保持不变的相邻行为
→ 保存 evidence.yaml
→ 不为一次性检查强制新建可复用流程

flow
→ 使用完整流程定义、可执行测试和运行证据
→ 新增独立业务路径时才新增流程和测试
```

开发阶段的编译、静态检查和单元测试一般不能代替流程级验证；只有路由明确选择 `self_check` 且实际结果直接覆盖全部验收时，才允许自检即验收。

## `targeted/flow` 的测试单元

测试以一个有业务意义、能够独立跑通并判断结果的流程为单元。

```text
一个测试类或测试文件
→ 对应一个业务流程、用户流程、数据流程或实验流程

一个测试方法或场景
→ 对应正常路径、关键分支或失败路径
```

不以简单函数为主要验收单元，也不把整个系统全部功能塞进一个测试。

## `targeted/flow` 的核心闭环

```text
确定需要验证的业务流程
→ 查找已有流程定义和测试
→ 优先复用；缺失时才新增
→ 确认本次预期保持不变还是按需求改变
→ 真实运行
→ Assert 验证
→ 保存证据
→ 通过，或修复后重跑
```

## `flow` 的三类必备产物

`policy: flow` 的每个流程必须能找到以下三类产物。新流程需要创建，回归直接复用已有流程定义和测试，只新增本次运行证据。

### 流程定义

一个 `.agentloop/flows/<flow_id>.yaml`，至少包含：

- 流程目标
- `covers.paths/interfaces/routes/db_objects/states/tags` 覆盖索引
- 前置条件
- 测试账号和数据
- 连续执行步骤
- 每一步预期结果
- 中间检查点
- 最终结果
- 关键失败路径
- 使用的执行器

### 可执行测试

必须是项目能够直接运行的测试类、测试文件或脚本。

测试必须：

- 准备或明确前置状态
- 按流程顺序执行
- 对关键检查点 Assert
- 对最终业务结果 Assert
- 失败时输出可定位信息
- 可以安全重复运行

### 运行证据

必须来自真实执行，至少包含：

- 测试命令
- 精确验证身份：`loop_id + requirement_version + scope + flow/check + tested_commit`
- 代码和测试版本、运行 ID 以及 `active / stale / superseded` 生命周期
- 环境
- 通过、失败和跳过数量
- 失败断言和堆栈
- 测试框架原始报告
- 日志、请求响应、数据结果或截图；按执行器产生

AI 阅读代码后推测“应该通过”不算运行证据。

使用 `flow_id` 时，不区分 UI、code 或 command 执行器，都必须由本次运行生成统一测试报告，并满足 commit、run nonce、断言数量、必需步骤和跳过项检查。`check_id` 可用于构建、lint、Schema 校验等结果由退出码完整定义的 targeted 命令；这类命令不得冒充业务 flow 覆盖。

`evidence --result` 是兼容性断言，只能与插件实际执行得到的 passed/failed 一致。`blocked` 表示执行前提不具备，应转换 Loop 状态并记录阻塞条件，不能伪造为测试运行结果。

### Evidence 选择与替代

Gate 必须按精确验证身份选择 Evidence，不得从其他需求版本、范围、流程或提交借用结论。同一 `loop_id + requirement_version + scope + flow/check` 的新运行一开始，旧的 `active` Evidence 即标记为 `superseded`；新运行失败或中断也不能恢复旧 passed 结论。需求、实现或测试基线变化时，只将受影响范围标记为 `stale`，保留历史证据用于追溯。

### 前后端真实数据链路证据

`integration_data.required: true` 时必须使用可执行自动化完成真实的数据库 → API → UI 验证：

1. 通过 seed、factory 或 fixture 向隔离测试数据库写入本次运行唯一 sentinel。
2. 调用声明的后端接口，断言响应包含同一 sentinel。
3. 打开声明的前端路由，断言页面通过接口查询并展示同一 sentinel。
4. evidence 的 `data_lineage` 分别记录数据库、后端、前端观察值及证据路径，并覆盖声明的全部数据库对象、接口和路由。

任一层缺失、覆盖不全或 sentinel 不一致均为 failed。页面能打开、静态文本可见、mock 响应或仅有 API 测试都不能替代该链路。

## 最小文件规则

`flow` 新建流程默认只保留：

```text
一个可复用测试流程 YAML
+ 一个测试类、测试文件或脚本
+ 工具自动生成的运行结果
```

这是新建流程时的最小产物。已有流程进行回归时，直接复用原测试流程定义和测试，只新增本次工具运行结果。

`targeted` 默认只新增 `evidence.yaml` 中的一次运行记录；复用流程时填写 `flow_id`，一次性命令填写稳定 `check_id`。已有测试或命令不足以可靠判断时，升级为 `flow`。`self_check` 只更新 `work.md`。

流程范围、环境、步骤、预期和状态合并在同一个 YAML 中。字段结构遵守[AgentLoop 产物与目录协议](../agentloop/产物与目录协议.md)。

成功时不再额外生成测试计划、执行记录、回归总结和最终报告等重复文档。失败时才增加问题记录和重跑证据。

测试分类只用于选择执行器和检查标签，不为每个标签建立独立流程。

## 回归复用规则

回归不是新的测试流程分类，也不新增执行器。

```text
已有流程，本次行为应保持不变
→ 直接运行原测试
→ 原步骤、断言和结果必须保持一致

已有流程，本次需求明确改变预期
→ 在原流程中更新受影响的预期和断言
→ 运行修改后的流程
→ 同时确认未声明改变的步骤和结果保持一致

本次新增了原流程无法表达的独立业务路径
→ 才新增可复用测试流程定义和可执行测试
```

回归范围根据开发交付的影响范围选择：

- 本次直接修改的流程
- 共用同一代码、接口、数据或状态的流程
- 必须保持不变的相邻流程
- 缺陷修复对应的原失败流程

回归默认产出只有新的运行证据。不要复制一份“回归流程文档”或“回归测试类”。

## 流程检索规则

测试 Agent 不按名称猜测已有流程，必须使用 `covers` 索引：

```text
接口、数据库对象、业务状态精确匹配
→ 优先

修改路径匹配
→ 其次

标签匹配
→ 最后补充
```

匹配到多个候选且无法确定时，路由置信度为 `low`，先确认影响范围。需求变化可能使已有流程失效时，将其标记为 `needs_review`，核对后再运行。

## 三种执行器

### 代码测试执行器

用于后端、接口、领域、数据、迁移和代码级端到端流程。

典型产物：测试类、测试脚本、Assert 结果、测试框架报告。

### UI 测试执行器

用于页面和用户点击流程。

典型产物：浏览器自动化文件、页面断言、步骤截图、失败录像。

### 命令与实验执行器

用于性能、安全、迁移命令、故障恢复和技术实验。

典型产物：可重复命令或脚本、原始指标、阈值断言和运行报告。

## 验证标签

接口、状态、权限、幂等、数据、安全等不是独立流程，而是流程的检查标签。

```yaml
checks:
  - response
  - state
  - database
  - permission
  - idempotency
```

标签决定流程中增加哪些断言，不产生一套新的流程。

## 失败与回归

失败后保存原始证据，判断是需求、设计、实现、环境、数据还是测试代码问题。

修复后至少重跑：

- 原失败场景
- 同一流程正常路径
- 受影响分支
- 必须保持不变的相邻流程

只有失败时才创建问题记录；成功流程不额外生成总结文档，测试报告和流程状态就是结论。

控制协议、Schema、Gate 或恢复逻辑发生变化时，回归不得只测正常通过路径，至少覆盖：

- 正常路径能通过；
- 缺项或伪造证据会失败；
- 修复后重跑能替代旧 Evidence；
- completion 拒绝后能回到最小受影响阶段；
- 旧版本产物能通过明确迁移或豁免路径恢复，不能被新门禁永久锁死。

## 完成条件

```text
self_check
→ work.md 中有实际检查命令、结果和验收结论

targeted
→ 定向检查真实运行
+ 关键结果有 Assert 或等价判定
+ 必验集合由独立基线重算且无缺项、无必需跳过
+ Evidence 与当前验证身份精确匹配并处于 active
+ evidence.yaml 已保存

flow
→ 流程定义存在
+ 可执行测试存在
+ 测试真实运行
+ 关键结果有 Assert
+ 必验集合由独立基线重算且无缺项、无必需跳过
+ Evidence 与当前验证身份精确匹配并处于 active
+ 运行证据已保存
+ 状态明确为 passed 或 failed
```
