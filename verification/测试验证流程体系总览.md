# 测试验证流程体系总览

## 总览职责

本总览是测试 Agent 收到 `ready_for_verification` 开发交付后的选择器和路由入口，只负责回答：

```text
当前需求要验证什么
→ 拆成哪些可独立验证的小流程
→ 每个小流程使用哪个执行器
→ 需要增加哪些检查标签
→ 进入对应的详细流程执行
```

产物约束、通过条件和失败处理遵循[测试验证流程定义规则](测试验证流程定义规则.md)，本总览不重复定义。

进入输入包括已确认需求和验收标准、实现代码、开发自检结果、影响范围以及测试交接信息。开发阶段的单元测试结果不能代替本阶段的流程验证。

复合 Loop 每次只接收一个 `ready_for_verification` 子流程，结果写回该子流程；其他子流程可以继续开发，父状态保持 `orchestrating`，直到聚合条件满足。

## Agent 选择流程

```text
读取需求、验收标准和开发产物
→ 根据 covers 索引查找已有流程定义和测试
    ├── 已有流程能够覆盖
    │   → 直接复用
    │   → 确认预期保持不变还是按需求改变
    └── 没有流程能够覆盖
        → 才拆出并新增可独立验证的小流程
→ 判断每个小流程需要什么方式取得可信结果
    ├── 代码、接口、数据或状态可直接断言
    │   → 代码流程验证
    ├── 必须经过真实页面操作并检查用户可见结果
    │   → UI 流程验证
    └── 必须运行命令、迁移、负载、故障或实验程序
        → 命令与实验流程验证
→ 增加必要的检查标签
→ 执行对应详细流程
```

回归验证不单独建立流程。它只是重新执行已有流程：

```text
预期未改变
→ 原测试和断言原样重跑

预期明确改变
→ 只更新原流程中受影响的预期和断言
→ 未声明改变的结果仍必须保持一致
```

检索顺序为接口、数据库对象和业务状态精确匹配，路径匹配，其次标签匹配。多个候选无法确定时不得猜测，按低置信度路由处理。

## 执行器入口

- [代码流程验证](flows/代码流程验证.md)
- [UI 流程验证](flows/UI流程验证.md)
- [命令与实验流程验证](flows/命令与实验流程验证.md)

一个小流程默认只选择一个主执行器。只有单个执行器无法覆盖验收结果时才组合，例如：

```text
下单流程
→ UI 执行器验证用户点击和页面结果
→ 代码执行器验证订单、库存和支付状态
```

## 分类标签

执行器确定“怎么运行”，标签确定“额外检查什么”：

```text
response
state
database
event
permission
idempotency
compatibility
migration
performance
security
```

标签只决定增加什么断言和证据，不再产生独立流程文档。

## 统一执行闭环

```text
流程定义
→ 可执行测试或脚本
→ 真实运行
→ Assert 或等价判定
→ 保存工具生成的运行证据
→ 通过，或修复后重跑
```
