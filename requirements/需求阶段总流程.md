# 需求阶段总览

## 总览职责

需求阶段负责把最初的问题或想法变成已经确认、可以交给开发阶段使用的需求。阶段数量是检查清单，不要求逐项停顿。

```text
产生需求
→ 根据原始输入形成 provisional 复杂度档位
→ 执行需求确认流程
    → 核对事实与当前现状
    → 为每项验收确定独立依据和稳定 acceptance_id
    → 将 trivial / standard / composite 档位确认为 confirmed
→ 形成已确认需求
→ 需求达到可开发状态
→ 进入开发流程选择
```

需求阶段决定“做什么以及怎样算完成”；开发阶段决定“编码前还需要准备什么以及怎样实现”。

## 分工职责

### 需求负责人

对以下内容拥有最终确认权：

- 要解决的问题和目标
- 用户、业务价值和优先级
- 功能范围与非目标
- 业务规则和关键约束
- 验收标准
- 需求原型
- 未解决问题是否可以接受

需求负责人可以是产品负责人、业务负责人、客户或被明确授权的人。

### 需求 Agent

负责：

- 记录原始需求
- 核对事实与当前现状，并区分事实和推测
- 提出澄清问题
- 识别歧义、冲突和遗漏
- 起草目标、范围和验收标准
- 建议需求分类
- 判断是否需要需求原型并协助制作
- 维护需求状态和产物

需求 Agent 不能把自己的推测当成需求，也不能冒充需求负责人确认范围、验收标准或原型。项目明确允许的自动 Gate 必须留下策略判定记录。

### 开发 Agent

只在需求达到可开发状态后进入：

- 读取已确认需求、分类、原型和约束
- 根据主要风险和不确定性选择开发流程
- 发现需求冲突、范围变化或无法验证的验收标准时，退回需求阶段

开发 Agent 不在开发流程中私自扩大或改变需求。

### 测试验证 Agent

对 `targeted/flow` 依据已确认验收标准设计和执行验证。`self_check` 由开发 Agent 直接检查；测试 Agent 发现验收标准不可执行或相互冲突时退回需求阶段，不自行改写需求。

同一个 Agent 可以承担多个角色，但切换角色时仍必须遵守各阶段的确认权限。

## 需求阶段主流程

```text
原始需求
→ [需求确认流程](flows/需求确认流程.md)
    → 核对事实与当前现状
    → 明确目标
    → 确认范围和验收标准
    → 完成需求分类
    → 判断并按需确认需求原型
    → 一致性检查
    → 需求确认 Gate
→ 需求达到可开发状态
→ [开发流程体系总览](../development/开发流程体系总览.md)
```

## 最小产物

`standard/composite` 默认只维护一个 `requirement.md`，包含：

- 原始问题和提出背景
- 已核对的当前事实、证据来源和待确认假设
- 目标用户、场景、问题和期望结果
- 目标、范围和非目标
- 业务规则与关键约束
- 可执行验收标准
- 每项验收的稳定 ID、独立事实源、允许偏差和可观察结果
- 主要类型、特征标签和分类依据
- 原型决定及原型引用
- 未解决问题
- 确认人、确认状态和时间

`trivial` 模式把需求与开发记录合并到 `work.md`。需要需求原型时，原型作为独立实际产物保存；评审意见直接更新需求记录或原型，不重复生成总结。

## 需求义务与独立基线

“按原型实现”“功能正常”“测试通过”不能直接作为验收标准。每项验收义务必须记录：

```text
acceptance_id
→ 独立依据：用户确认、原型源码、业务规则、外部规范、数据约束或现有行为证据
→ 可观察的正常结果
→ 必须覆盖的分支、失败和权限结果
→ 允许偏差及理由
→ 需求变化时的失效范围
```

需求阶段只定义做什么和怎样算完成，不指定测试实现细节；但必须保证开发和测试可以分别从同一独立基线建立映射。事实、推测、实现建议和验收义务不得混写。

## 快慢路径

```text
trivial
→ draft 初判为 provisional，需求核对后才能 confirmed
→ 需求确认流程阶段 1—9 可在一轮完成
→ 未触发阶段不建空章节
→ 项目策略允许时自动通过需求确认 Gate

standard
→ 连续阶段可合并执行
→ 只在证据不足、冲突、原型评审或人工 Gate 停下

composite / epic
→ 先确认总体边界和拆分依据
→ 再由子流程或子 Loop 使用同一需求版本
```

复杂度模式不替代需求主要类型；需求类型用于补充核对，复杂度模式用于决定文件开销和调度方式。

## 需求原型边界

需求原型回答：

```text
做什么
→ 给谁使用
→ 核心页面或业务流程是什么
→ 用户怎样完成主要任务
```

开发设计原型回答具体页面状态、组件行为、响应式和实现数据需求。开发设计原型改变范围、核心流程或验收标准时，必须退回需求阶段。

## 可开发状态

```text
目标明确
+ 关键事实和现状已经核对
+ 范围和非目标明确
+ 关键业务规则与约束明确
+ 验收标准可以实际验证
+ 每项验收有稳定 ID、独立依据和可观察结果
+ 需求分类完成
+ 需要的需求原型已经确认
+ 阻塞问题已经关闭
+ execution_profile.status == confirmed
+ 需求确认 Gate 已通过
→ ready_for_development
```

达到可开发状态不等于立即编码，只表示允许进入开发流程选择。

## 后续扩展

当前先保留一个通用需求确认流程。以后只有出现明显不同的确认路径时，才在 `requirements/flows/` 增加流程，例如探索型需求、合规型需求或紧急缺陷需求；不按需求类型机械复制多套确认流程。
