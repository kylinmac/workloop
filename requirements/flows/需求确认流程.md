# 需求确认流程

## 流程目标

将原始问题、想法或请求转化为需求确认 Gate 已通过、验收标准可执行的需求。

## 进入输入

至少具备以下一项：

- 一个需要解决的问题
- 一个产品或业务想法
- 一个明确的变更请求
- 一个问题现象或技术治理目标

## 裁剪规则

十个阶段是检查项，不是十次会议、十份文档或十个人工停顿。

收到任务后先根据已知信息记录 `execution_profile.status: provisional`；完成事实、范围和验收核对后重新判断，阶段 10 前必须设为 `confirmed`。

```text
trivial
→ 阶段 1—9 在一次调查和一次 work.md 更新中完成
→ 未触发的原型阶段直接跳过
→ 满足项目自动确认策略时，阶段 10 自动通过

standard
→ 允许合并连续阶段
→ 只在事实不足、范围冲突、需要原型或人工 Gate 处停下

composite / epic
→ 先确认总体目标、边界、验收和拆分依据
→ 子流程或子 Loop 只补充自身范围，不复制总体需求
```

合并阶段不等于省略产出。目标、范围、验收、分类、原型决定和确认依据仍必须能够在正式需求记录中检查。

`trivial` 资格条件由[AgentLoop 产物与目录协议](../../agentloop/产物与目录协议.md)统一定义；任一条件不满足立即升级，不强行走快车道。

## 阶段、产出与职责

| 阶段 | 需求 Agent 操作 | 明确产出 | 谁确认 | 检查与出口 |
|---|---|---|---|---|
| 1. 记录原始需求 | 保留提出者的原始表达，补记提出背景、用户和场景，并初判复杂度 | 原始需求、背景、初始状态和 `provisional` 执行档位 | 提出者或需求负责人 | 原始问题未被改写成方案；已进入轻量、标准或多切片候选路径 |
| 2. 核对事实与现状 | 对现有页面、流程、接口、数据、日志、代码或业务记录进行必要调查；从 0 建设时核对可复用能力和已有约束 | 当前事实、证据来源、已证实内容、待确认假设 | 事实提供方或需求负责人 | 事实与推测已经分开，关键现状有可追溯证据 |
| 3. 明确问题与目标 | 基于已核对事实，询问当前问题、期望结果、价值和成功表现 | 目标用户、使用场景、当前问题、期望结果、需求目标和成功标准 | 需求负责人 | 目标描述结果而非预设实现，关键歧义已关闭 |
| 4. 确定范围 | 拆出本次做什么、不做什么、边界、依赖和关键约束 | 功能范围、非目标、业务规则、权限、安全、性能和兼容约束 | 需求负责人 | 范围能够判断包含或排除，依赖和约束明确 |
| 5. 形成验收标准 | 将目标和规则改写成可以观察或运行验证的场景 | 正常、关键分支和失败场景的验收标准 | 需求负责人；测试 Agent 可检查可执行性 | 每条标准有前置条件、操作或事件、预期结果；无“体验良好”等无法判断表述 |
| 6. 完成需求分类 | 根据变化性质建议主要类型和特征标签，并执行被触发的补充核对 | 主要类型、特征标签、分类依据、补充核对项和回归重点 | 需求负责人确认事实；需求 Agent 维护分类 | 分类与目标、范围和现有事实一致，触发项已经补齐 |
| 7. 判断需求原型 | 判断核心页面、操作路径或业务流程是否仍有多种理解 | `需要` 或 `不需要`、判断依据和最小原型形式 | 需求负责人 | 决定能够解释为什么原型能减少当前不确定性 |
| 8. 按需确认原型 | 制作最小必要原型，组织实际操作、评审和修改 | 已确认需求原型、主要用户路径及原型引用 | 需求负责人及必要业务方 | 原型可完成核心路径，并与范围和验收标准一致 |
| 9. 一致性检查 | 对照事实、目标、范围、规则、验收标准、分类、原型和复杂度档位，列出冲突与未决问题 | 更新后的需求记录、`confirmed` 执行档位、未解决问题及处理状态 | 需求 Agent 执行；阻塞项由需求负责人决策 | 每项目标有验收方式，档位与真实拆分规模一致，阻塞问题为零 |
| 10. 正式确认 | 计算待确认产物摘要并执行需求确认 Gate | 有效人工审批事件，或符合策略的自动确认记录 | 需求负责人或项目审批策略 | 可开发状态全部条件满足，确认绑定当前需求版本和产物摘要 |

除需求原型外，上述产出默认更新在同一个需求文件中；`trivial` 模式更新在 `work.md`。

## 需求原型判断

```text
核心页面、业务流程或用户路径仍可能有多种理解
→ 需要需求原型

文字、现有交互或既有规则已经足以唯一确定需求
→ 不需要需求原型
```

原型形式只做到消除当前需求歧义：

```text
业务步骤不明确 → 业务流程图
页面结构不明确 → 线框图
操作路径不明确 → 可点击原型
视觉结果本身是需求 → 高保真原型
```

## 事实与现状核对最低要求

```text
从 0 建设
→ 核对是否确实没有可复用系统、模块或既有规则

新增或修改
→ 核对当前页面、流程、接口、数据和实际行为

缺陷修复
→ 核对问题现象、实际结果和预期行为依据

内部改进
→ 核对当前基线、外部行为和需要改善的指标

迁移升级
→ 核对当前版本、数据、配置、依赖和运行状态

下线删除
→ 核对真实使用方、调用方、数据和依赖
```

AI 阅读需求后的推测不算事实。事实应引用可检查的系统、数据、代码、日志、页面、规则或负责人确认。

## 验收标准最低要求

每条验收标准至少能够回答：

```text
在什么前置条件下
→ 谁执行什么操作，或发生什么事件
→ 系统或业务必须产生什么可观察结果
```

性能、安全、兼容和数据正确性要求应给出可判断条件或阈值。

## 退回规则

出现以下情况时返回对应阶段：

```text
目标发生变化
→ 返回阶段 3

范围、规则或约束发生变化
→ 返回阶段 4，并同步更新验收标准

原型改变核心流程或功能范围
→ 返回阶段 4 和阶段 5

开发阶段发现验收标准不可执行或设计必须改变需求
→ 返回阶段 5 或更早阶段
```

## 确认信号

人工确认必须由宿主 UI、CLI 或 API 形成绑定 `loop_id`、`requirement_version`、产物摘要、确认人、结论和来源事件 ID 的审批事件。Agent 不得自行代填人工确认。

用户在对话中回复“可以”，只有被宿主记录为上述审批事件时才算正式确认。

项目配置允许 `auto_high_confidence` 时，只有 `trivial`、高置信度、无禁止标签且无未决问题的需求可以自动通过。具体规则遵守[AgentLoop 状态机](../../agentloop/AgentLoop状态机.md)。

delivery 子 Loop 完全派生自父 Loop 已确认范围时，可以引用父审批自动通过；新增范围、验收、规则或风险时必须独立确认。

## 完成条件

```text
目标明确
+ 关键事实和现状已经核对
+ 范围和非目标明确
+ 关键规则和约束明确
+ 验收标准可执行
+ 需求分类完成
+ 必要原型已确认
+ 阻塞问题为零
+ execution_profile.status == confirmed
+ 需求确认 Gate 已通过
→ ready_for_development
```
